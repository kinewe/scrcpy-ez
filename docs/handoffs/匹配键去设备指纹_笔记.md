# 笔记：配方匹配键不要带设备指纹（给 codex 参考）

日期：2026-10-31
背景：rc23 的 `NativeAlphaPolicy` 已实现"配方缓存 + 命中复用"（结构指纹 + 环境匹配 + 步骤白名单），方向正确。本笔记只针对**匹配键**的一处风险。

## 问题：`platform` 判断包含 serial / fingerprint

代码位置：`server/src/main/java/com/genymobile/scrcpy/NativeAlphaPolicy.java`（`plan()` 内）

```java
boolean platform = serial.equals(env.optString("serial"))
        && environment.optInt("sdk") == env.optInt("sdk")
        && environment.optString("fingerprint").equals(env.optString("fingerprint"))
        && environment.optInt("userId") == env.optInt("userId")
        && environment.optInt("uiMode") == env.optInt("uiMode");
```

**后果（已实测）**：
- 平板（25091RP04C）上规划成功的配方 → 换到手机（K80）时，`serial` 与 `fingerprint` 不同 → `platform=false` → 不匹配
- 于是退回现场规划（discovered）→ 对未知结构试错 → **闪退**（"平板换手机同一个微信都自动不了直接崩"）
- 这违背"规则化"的初衷：**同一款应用、同样的页面结构，本应复用同一套处理流程**

## 建议：把"设备指纹"换成"能力分组"

匹配键改为：

| 键 | 说明 |
|---|---|
| `treeSignature` | 结构指纹（相机类型 + 祖先链 + 背景层）——**已有，保留** |
| `application`（versionCode / versionName / signingSha256 / lastUpdateTime） | 应用版本与签名——**已有，保留** |
| **`capability`**（新增） | `sdk` 版本段（如 34/35/36）+ 厂商（可选）+ 关键 API 可用性（能否调 `ScreenCapture.captureLayers`、`VirtualDisplay` 的 alpha 行为） |
| `userId` / `uiMode` | 可保留（多用户/夜间模式可能影响窗口结构），但建议单独评估必要性 |
| **`serial` / `fingerprint`** | **移出匹配键**；仅写入日志与 diagnostics，用于定位，不参与命中判定 |

## 预期收益

1. **同应用同结构跨设备复用**：平板→手机不再退回试错，减少崩溃
2. **首次之后都命中**：真正的"又快又准"（而不是"只在本机又快又准"）
3. **符合规则化方向**：匹配的是"结构 + 能力"，不是"某一台设备"

## 边界与注意

- **能力分组要谨慎**：不同厂商 ROM 的 `VirtualDisplay` / `captureLayers` 行为可能不同 → 可用"厂商 + sdk"作为能力标签，而不是整串 `fingerprint`
- **保留诊断价值**：`serial`/`fingerprint` 仍写入日志，便于"同配方在不同设备失败"时定位
- **迁移**：已有配方数据（含 serial/fingerprint 的环境块）可保留字段但不再参与匹配；新配方按 capability 写入
- **回退**：capability 匹配失败时，仍可退回"现场规划"（不变）

## 一句话

**"匹配"的方向是对的；只是匹配键里带着设备指纹，会让"匹配"退化成"只在本机有效"。把键换成"结构 + 能力"，才是规则化应有的样子。**
