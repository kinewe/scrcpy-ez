# 合成前 UI 原生 Alpha：接口与实测

日期：2026-10-31。限制：ADB、免 root；不安装/启动桥接 APK，不修改目标 APK。纯 shell 允许在独立 app_process 中运行临时 DEX。目标是快速、准确获得相机覆盖 UI 的 RGBA/A8，不通过背景颜色反推透明度，不人为降低整个窗口 alpha。

实验根目录：`<historical-workspace>/alpha-buffer-research-20261031/`。下列日志、源码与清单均在该目录。

本轮暂停增加应用规则。实验放在独立目录，RC23 Engine 16 运行包与现有档案未修改。手机界面由用户操作；探针没有发送点击/返回、启动/强停应用，也未触发透明场景过渡。

## 已得到的关键结果

**Steam 原始页面确实能重绘出独立的透明 UI；现有全 255 的系统捕获不能证明 UI Alpha 不存在。**

用户在手机本机打开 Steam 扫一扫，未开启 RC23，也未修改 View、背景、窗口格式或 opaque 标志。正常 IWindow 与无输入通道的 SurfaceView 图层须区分：前者可执行 ViewDebug，后者不能作为第二个应用窗口。

一次根 UI 重绘对照：

| 项目 | 实测 |
|---|---:|
| 预览 SurfaceView | 1 个，保持正常预览 |
| UI 图尺寸 | 1440 × 3200 |
| A=0 | 3,195,023 像素 |
| 0<A<255 | 389,957 像素 |
| A=255 | 1,023,020 像素 |
| 输出 PNG | 189,273 字节 |
| 命令内重绘、编码与管道返回 | 360.873 ms |

这次 PNG **只作诊断对照**，不接回实时方案。它证明应用在未被透视机制修改时，可以输出带透明孔洞、半透明 UI 的独立重绘结果；**不等于已经直接取得屏幕正在使用的原始生产者缓冲区**。时间也不是单独 PNG 编码耗时。

稍后预览自行暂停：SurfaceView 数量为 0，同样根重绘的 4,608,000 个像素全部 A=255，耗时 322.825 ms。这一阴性对照说明预览是否存在对 UI 孔洞有直接影响。

证据：`run-compare-png-0-com.valvesoftware.android.steam.community.log`（该文件被后续运行覆盖，已将首次阳性输出另存 `steam-ui-replay-control-positive.txt`）；后续暂停对照另存 `steam-ui-replay-control-paused.txt`。

## 旧路径为什么产生大量背景规则

SurfaceView 常规模式并不是把相机画进 UI 缓冲区。UI 绘制会为独立相机 Surface 打孔，系统再合成相机与 UI。孔洞本身也会清除相机区域下面的背景，因此无需逐个识别其祖先 Drawable。

AOSP 参考中，`draw/dispatchDraw` 在绘制完成且相机不在 UI 之上时调用 `clearSurfaceViewPort`；孔洞强度与 View alpha 有关。具体实现须以设备行为为准。

本轮在 shell 自有、未挂屏的 SurfaceView 上做独立 GPU 对照。画布 64×64，原先画满不透明背景；48×48 相机区域上方绘制 alpha=128 的扫描线。只为独立模型设置自有对象的绘制完成/合成顺序状态，未修改真实应用。

| 自有 SurfaceView 模型 | A=0 | A=128 | A=255 |
|---|---:|---:|---:|
| 在 UI 下方，alpha=1，正常打孔 | 1920 | 384 | 1792 |
| 在 UI 下方，alpha=0 | 0 | 0 | 4096 |
| 在 UI 上方，不再打孔 | 0 | 0 | 4096 |

因此，“先把相机 View alpha 改成 0/置顶，再读 UI”可能同时破坏自然孔洞；接着逐层清背景，是在补偿这个行为。它不是简单地从已有 UI 图中移除相机。

这不等于所有旧成功样本都无效；它解释了旧策略在另一类渲染结构上为什么需要越来越多恢复/背景规则。应优先保留原始 UI 绘制，只在读出阶段分离独立相机 Surface。

证据：`run-hole-lab.log`，最终三组断言通过。

## 直接读取事务中的原始 HardwareBuffer

### 自有缓冲区：读取可行且 A8 精确

系统的 SurfaceControl 事务在含有真正 BufferData 时，可以通过 GraphicBuffer 的标准 Parcel 格式导入 HardwareBuffer，无须截图或 PNG。探针限定尺寸、格式、传输长度/FD 数等字段；仅在自有缓冲区执行像素读取。

自有 64×64 图像的四档 Alpha，各占 1024 像素，逐档读取结果：

```
A=0:1024  A=64:1024  A=128:1024  A=255:1024
```

这里没有颜色反推、整窗半透明，也没有编码图像。它验证了“拿到真实缓冲区后如何无损提取”的部分，**未验证跨应用持续取得该缓冲区**。

证据：`run-lab.log`。

### 真实 Steam：当前同步入口没有交出像素

| 实验 | 结果 |
|---|---|
| 手机本机，同尺寸窗口同步，4 次 | 无 FD，无 GraphicBuffer，无 buffer 变更位 |
| 附加空 bounds-change transaction 请求下一次绘制，2 次 | 仍无像素缓冲区 |
| 用户关闭最近任务后重新启动，观察新任务及 Splash→主窗口，8 次 | 捕获到新窗口图层，仍无像素缓冲区 |
| 请求窗口高度差 1 像素并在 finally 恢复，1 次 | 同样没有像素缓冲区；不能证明全屏模式下有效分配尺寸确实变化，因此不能将此条当作“所有重分配均失败”的证据 |

实际主要状态的 `what` 是 `0x80100000` 等图层信息；没有 AOSP 对应的 `eBufferChanged=0x00200000`。原始回调 Parcel 与反序列化后再次写出的 Parcel 都做了检查，不能归因于探针二次序列化才丢掉缓冲区。

AOSP 的事务序列化还存在缓存命中后只发送 buffer ID 的情况。但本轮观察到的是没有 buffer 变更位，不应直接归类为缓存命中，更不能把 layer ID 当成可读取像素的凭证。

同步回调耗时约 9–45 ms，只是图层同步时间，**不是图像获取延迟或原生 Alpha 帧率**。

证据：`steam-physical-same-bounds.log`、`run-task-draw-0-com.valvesoftware.android.steam.community-2.log`、`run-watch-com.valvesoftware.android.steam.community.log`、`run-task-resize-0-com.valvesoftware.android.steam.community-1.log`。

## 只捕获 UI 窗口，排除相机子树

`ScreenCapture.captureLayers` 会按图层树生成新的结果；当前名为 window-buffer-layer 的路径仍是这类捕获，不能称为直接复制生产者缓冲区。

系统支持 `setExcludeLayers`。这是优先候选：保留 UI 原始孔洞，同时仅在捕获输出中排除相机子 Surface。它不要求清理 Drawable，也不应改变 View 的 alpha/Z 或页面生命周期。

本轮已在图层快照中识别真实 UI 窗口及其 Bounds 子容器，并验证所属 UID/父链；但 WindowOrganizer 回调提供的是系统窗口容器和 UI 根句柄，没有交出该 Bounds 子容器的句柄。因此探针在缺少准确句柄时拒绝捕获，没有用伪造 layer ID 或不匹配 Binder 冒充。

AOSP JNI 明确使用 SurfaceControl 的 Binder handle 来选择根和排除项，单有图层编号不能代替该句柄。这一入口尚未打通，不能报告“已可直接排除 Steam 相机”。

证据：`run-task-ui-0-com.valvesoftware.android.steam.community-1.log`。此项失败是句柄不足，**不是 UI Alpha 阴性**。

## 应用内部原生重绘接口

本机实际接口枚举：

- ViewDebug 可以执行 capture/captureLayers，也有进程内 rendering-commands capture。
- IWindow 暴露 executeCommand 与 requestScrollCapture，没有枚举到通用固定页面的“输出原始 UI 到调用方 Surface”方法。
- RenderNode 不可 Parcelable。ViewDebug 基本类型调用不能把另一个进程的 RenderNode/HardwareRenderer 导出为可继续调用的远程对象。
- 设备 RenderNodeStub 扩展提供本地 view/canvas、begin/endRecording 等方法，未发现远程缓冲区导出接口。
- Steam 与微信均 debuggable=false、profileableByShell=false。本轮没有更改调试设置、附加进程或替换 APK。

已有研究核实 ScrollCapture 会用 opaque=false 的独立 HardwareRenderer 回放根 RenderNode，并可向调用方 Surface 输出，无需 PNG。但微信扫一扫此前返回“No scrollable targets”；不能把它外推为所有固定页面都能接入。未在本轮伪造滚动布局或安装回调。

证据：`actual-apis.log`；历史对照 `<historical-workspace>/srgb-alpha-research-20261028/内部渲染器研究记录.md`。

## 更本质的边界

| 渲染结构 | 所需入口 |
|---|---|
| 独立 SurfaceView 相机 + 能自然打孔的 UI 窗口 | 原始 UI 缓冲区，或保留孔洞并排除相机子树的系统捕获 |
| TextureView 相机被画进同一个 HWUI 窗口 | 合成前的 UI/RenderNode 回放；仅复制最终窗口缓冲区仍可能包含相机 |
| 相机和 UI 在单一 GL/Flutter 自绘目标中合成 | 应用/引擎内部绘制入口；系统看到的提交图像不保证还有独立 UI 图 |

不能由“总有合成步骤”推导出“一定有可跨进程访问的整页透明 UI 纹理”。同样，不透明合成图的 RGB 也不能唯一确定原 UI 的颜色与 alpha；本轮不将反推当作原生通道。

## 研究结论与下一步验收条件

本轮没有找到已验证的通用高速导出入口，也没有新增成功档案。得到的是两个有直接证据的方向修正：

1. Steam 的原始 UI 重绘可以有 Alpha，不能继续把捕获全 255 当作应用没有通道。
2. 对独立 SurfaceView，应保留 UI 自然孔洞，优先在系统图层/缓冲区读取阶段分离相机；先隐藏 View 可能破坏目标信息。

后续投入集中在两个可独立验收的接口问题：

- 合法取得相机子树句柄或原始 UI GraphicBuffer，保留原始绘制状态。
- 对没有独立 UI 缓冲区的路径，寻找系统允许的原生 UI 回放到 Surface 的入口；没有证明入口前不扩大应用规则库。

成功条件必须同时包括：真实目标缓冲区/绘制来源、逐像素 A8 保真、持续新帧、明确的 fence/帧身份、完整 UI、相机业务不因读取被破坏、无页面重建循环。仅有 metadata 回调、RGBA8888 格式、非零 Alpha 或 shell 自有图像都不能算目标应用成功。

实现：`TransactionBufferProbe.java`、`run_probe.py`。临时 DEX 只运行在 shell 独立进程。所有创建的自有 Surface/HardwareBuffer/Renderer 均在完成后释放或进程结束回收；唯一尺寸变化请求在 finally 提交原尺寸恢复，随后用户重新打开的 Steam 任务已是正常原始任务。
