# AndroMeld 相机层方案：逆向与 Windows 实测

日期：2026-10-28。分析对象为用户提供的 APK、K80 已安装 helper，以及官方 Windows 浏览器入口。本次未修改 AndroMeld，未绕过收费或权限确认，未复制产品代码到 EZ。

## 结论

**对本次 APK + Windows Web 路径，归类为 C：相机与 UI 完整合成后作为普通视频回传。没有发现 A（captureLayers 排除相机）或 B（特定 VirtualDisplay flag 排除 SurfaceView）的实现证据。**

这不是通过“黑色背景看起来不透明”推断的：SurfaceFlinger 的实际显示输出列表明确包含全屏相机 SurfaceView，且相机层 `isOpaque=true`、UI 层 `isOpaque=false`。OWN_CONTENT_ONLY 配置确实存在，但没有排除相机。

**Mac 演示中的桌面透视模式仍不能据此定案。** 本次 Windows Web 没有出现屏幕摄像头／透视入口，没有复现该功能，也没有取得原生 Mac 客户端二进制。Mac 侧色键、本地合成、其他输出通路或版本差异都不能仅凭本次结果确认为事实。

## 动态证据：不是只有相机层存在，而是它确实进入输出

用户批准连接后，在 Windows 上连接 AndroMeld Web，打开企业微信。先采集普通主页面，再由用户进入扫一扫，读取显示、SurfaceFlinger、CameraService 与 VirtualDevice 的只读信息。未截取聊天内容，原始日志只保存在本地 `private-work/`。

设备为 REDMI K80 / Android 16 / SDK 36。企业微信显示为 `AndroMeld Fusion`，displayId 42；采样时尺寸 760×1086、128 DPI，owner 为 `com.android.shell`、UID 2000。

普通页没有企业微信扫一扫的 SurfaceView。进入 `LoginScannerActivity` 后，出现以下独立层关系：

```text
LoginScannerActivity UI #20887：PREMULTIPLIED，isOpaque=false
  相机 SurfaceView 容器 #20889
    相机 BLAST 缓冲 #20890：NONE，alpha=1，isOpaque=true
```

关键是实际显示合成器的 `layerStack=42` 输出中同时包含：

1. 相机 BLAST #20890：输出区域 `[0,0,760,1086]`，源相机裁剪 `[0,0,720,480]`，旋转 90 度。
2. LoginScannerActivity UI #20887：整个应用区域。
3. 应用侧边 Panel #20895。

这直接说明本次 Windows 路径没有把相机排除。不能把 `usesClientComposition=true` 误读为电脑客户端合成；它表示 Android SurfaceFlinger 的 GPU 合成路径。

AndroMeld 也确实创建了 shell 所有的 VirtualDevice，并为每个显示注册两路虚拟相机。Agent 日志包含 `mediaPolicies=true, macCamera=true`。但 CameraService 显示本次企业微信实际打开的是**物理 Camera ID 0**，而非该 VirtualDevice 注册的 `v25_1022/v25_1023`。因此，本次没有完成虚拟摄像头输入和 Mac 屏幕摄像头的性能验收，不能将注册成功当作已使用成功。

具体摘录见 图层证据摘录.txt（本地历史证据，未公开），结构化核验见 EVIDENCE.json（本地历史证据，未公开）。

## 静态证据及排除误读

| 位置／线索 | 查到的实际用途 | 对问题的意义 |
|---|---|---|
| `s0.f0` | DisplayManager 镜像回退、own-content VirtualDisplayConfig、VirtualDevice 显示桥接 | 普通显示创建；没有找到按相机子层过滤 |
| `A.c` / `s0.r2` | 老式 SurfaceControl 显示镜像与显示电源管理 | 不能把出现 SurfaceControl 认作 captureLayers |
| `captureLayers` / `captureDisplay` / `setExcludeLayers` / `excludeLayer` | APK DEX 中未找到相应引用或字符串 | 结合实际输出，可排除“本次路径正在使用这些 API 过滤相机”的解释；仅字符串缺失本身不是万能证明 |
| `D0.k` / `D0.g` 的 ImageReader | 用于 `andromeld-widget-*` 的 Presentation；回调获取最新 Image 后直接关闭 | 不是 RGBA UI 逐帧传输来源 |
| `MirrorServerMain` | MediaCodec 输入 Surface、H.264 / HEVC、常规编码参数 | 当前应用显示回传为普通视频路径 |
| `s0.B1` 等虚拟相机桥接 | VirtualCamera 注册、JPEG 解码、Canvas 写入相机 Surface | 是电脑到 Android 的相机输入方向，不是排除相机的 UI 输出方向 |
| `hasAlphaChannel` / `setHasAlphaChannel` | WebRTC EGL 配置库 | 不能证明远端应用视频保留原生 alpha |
| `alpha.jpg` | 与 `beta.png` 配对的文件列表协议测试数据 | 与透明层传输无关 |
| `getTransparentRegion` | Drawable 包装类 | 与目标应用 SurfaceView 排除无关 |

公开 Web 主脚本包含 WebCodecs VideoDecoder、低延迟解码设置及摄像头 JPEG 桥接；没有发现屏幕采集调用或本次关心的透明 UI 合成实现。这里只限定到核验过的 Web 131 主脚本，不将其外推为原生 Mac 代码。

## 流畅度结论的边界

读取相机 BLAST 层的 SurfaceFlinger `--latency`，获得 127 个有效帧时间戳，约 24.94fps，帧间隔中位数 41.69ms。

这是 Android 相机 Surface 的局部呈现统计，**不是 Windows 浏览器渲染帧率，也不是拖动、桌面捕获、传输、扫码处理和返回显示的端到端延迟**。本次不据此评价 Mac 演示是否更快，也不将普通窗口测试算作 Windows 透视模式成功。

## EZ 可复用性

- 已确认的 own-content + VirtualDevice + VirtualCamera 思路，EZ 在 rc19 已有相同类别的基础能力；没有找到能直接补上“实时独立原生 UI alpha”的新 API 或特殊 flag。
- 动态 owner UID 2000 证明这些已使用的显示和虚拟相机功能可在 shell 权限下运行，无需 root。这不证明 shell 能取得第三方 app 的任意子层 SurfaceControl handle，也不证明可以使用 exclude-layers。
- APK 的普通镜像可覆盖较早版本，但本次 own-content 实测为 Android 16；其 Android 16 虚拟媒体分支有 SDK 检查。未经实测，不能承诺 Android 14/15 获得同等相机能力。
- 原生 Mac 若采用色键或本地合成，只能在进一步验证后独立实现其技术思路；不能把它当成已确认的原生 alpha 路线。
- 真正尚待解决的仍是：有界获取目标 UI 层、排除相机及其背景层，同时保持动画与布局跟踪。单纯更换编码、压缩格式或显示 flag 不能从已合成画面恢复原始 alpha。

当前证据不支持因此替换 rc19 的原生 PNG／混合实验。保留既有基线，后续优先取得与演示对应的 Mac 版本或新增 Windows 透视功能的明确版本，先判定“相机输入与 UI 合成分别在哪里发生”，再进行同尺寸、同设备、同网络的端到端对照。
