## 0. 结论摘要

### 0.1 一句话

1. **问题一（相机子层句柄）在本轮证据下“不可行”**：shell 能合法拿到的最底层句柄是 WM 的 WindowState/BLAST 窗口根层（设备已实际收到 56109 句柄）；相机 `SurfaceView` 子层和 `Bounds for - <window>` 子层都是**应用进程创建**的层，句柄从不跨进程外流，没有任何公开/隐藏 Java API 可由 layerId 反查句柄，伪造 `LayerHandle` 会被 SurfaceFlinger 直接拒绝。因此“`captureLayers` + `setExcludeLayers` 排除相机子树”这条路对普通 `SurfaceView` 相机页**走不通**。
2. **问题二（UI 原生重绘导出到自有 Surface）有唯一有希望的通道**：shell 已持有 IWindow token（上一轮实测），可**直连** `IWindow.requestScrollCapture`（应用侧 `ViewRootImpl.W.requestScrollCapture` 无任何权限校验，绕开 `WindowManagerService.requestScrollCapture` 的 `READ_FRAME_BUFFER` 检查），从 `ScrollCaptureResponse` 拿到应用内的 `IScrollCaptureConnection` binder，调用方**自带 Surface** 调 `startCapture(Surface, IScrollCaptureCallbacks)`，应用内 `ScrollCaptureViewSupport` 用 `HardwareRenderer.setOpaque(false)` 把**整棵根视图 RenderNode**（含 SurfaceView 的透明洞 `punchHole` op）回放到我方 Surface，`requestImage(Rect)` 逐帧驱动。**硬门槛：目标窗口内必须存在“可垂直滚动（canScrollVertically）”的可见 View 作为 target**；固定相机页（Steam 扫一扫、微信扫一扫已实测）返回“无可滚动目标”，该通道对该类页面**不可用**。
3. **问题三（同步事务是否带像素）已否认**：WM 的同步事务由 `BLASTSyncEngine` 用 **WM 自己的 Transaction** 合并各 `WindowContainer.mSyncTransaction`（layer_state_t 元数据）后交给回调；应用像素由 `BLASTBufferQueue.mSyncTransaction.setBuffer(...)` 在**应用进程**直接 apply 给 SurfaceFlinger，不进入 WM 事务。旧设备日志反序列化回调 Parcel：`fds=false rawBuffers=0`。因此“窗口同步只交图层信息、没有像素缓冲区”成立；除 `captureLayers` 之外没有其它合法取得应用 UI 图层像素的跨进程路径（详见 §3）。
4. **产品含义**：对“独立 SurfaceView 相机 + UI 窗口”的应用，若其页面**恰好有滚动容器**，`ScrollCapture→自有 Surface` 是唯一可实时、免 PNG、保真 A8 的通道（帧率由我方 requestImage 驱动）；对固定相机页，只剩 `ViewDebug CAPTURE` 的 PNG 重绘（实测 ~2.8 fps，360 ms/帧），不适合实时叠加，只能作诊断/兜底。

## 1. 问题一：从 shell app_process 合法取得应用窗口后代 SurfaceControl 句柄

### 1.1 图层身份模型：为什么“知道 layer ID”不等于“拿到句柄”

AOSP16 的跨进程图层身份有三段：

1. **SurfaceFlinger 侧的 `LayerHandle` Binder**：`LayerHandle` 是 SF 内部创建、注册为 binder 的对象，接口描述符 `"android.Layer.LayerHandle"`（**LayerHandle.cpp:35**），`LayerHandle::getLayer(binder)` 只接受这一 descriptor 的 binder 并 cast（**LayerHandle.cpp:37-58**）。
2. **Java `SurfaceControl` 的 Parcelable 载荷**：`{ISurfaceComposerClient binder, mHandle binder, layerId int, name, transformHint, width, height, format}`（**frameworks/native/libs/gui/SurfaceControl.cpp:238-279**，抓取件 `native_SurfaceControl.cpp`）。只有同时拿到 **client binder + handle binder + layerId** 才能反序列化出一个可用的 `SurfaceControl`（`SurfaceControl.java:1525-1552,1559-1577`；JNI `nativeReadFromParcel`/`nativeWriteToParcel`：**android_view_SurfaceControl.cpp:1978-2015**）。
3. **SF 按 handle 解析层**：`captureLayers` 用 `LayerHandle::getLayer(args.layerHandle)`（**SurfaceFlinger.cpp:7562-7564**，无效 handle→“captureLayers called with an invalid or removed parent”）；排除列表用 `LayerHandle::getLayerId(handle)`（**SurfaceFlinger.cpp:7590-7595**，无效→“Invalid layer handle passed as excludeLayer to captureLayers”）。

**由此得到问题一的第一性结论**：shell 想排除相机层，必须拿到**那个层的 LayerHandle Binder**；layer id（dumpsys/perfetto 能看到的）只是 handle 对应的数字，**没有任何 API 能由 id 反查 handle**（见 §1.2 D）。`CaptureArgs.excludeHandles` 的类型就是 `IBinder[]`（**CaptureArgs.aidl:61-62**），JNI 用 `excludeObject->getHandle()` 填 native handle（**android_window_ScreenCapture.cpp:173-187**）——所以“用伪造 binder/空 binder 占位”必然被 SF 拒绝。

### 1.2 逐通道分析

#### A. `WindowInfosListener` / `InputWindowHandle`（含 `touchableRegionSurfaceControl` 字段）

- Java 侧 `InputWindowHandle` 确实有 `public WeakReference<SurfaceControl> touchableRegionSurfaceControl`（**InputWindowHandle.java:145**）与 `setTouchableRegionCrop()`（:251-261）。
- 但两方向要分开看：
  - **Java → native**（把 Java `InputWindowHandle` 写进 `gui::WindowInfo` 给 WM/SF）：JNI 会 promote 这个 weakref 并写 `windowInfo->touchableRegionCropHandle = ctrl->getHandle()`（**android_hardware_input_InputWindowHandle.cpp:173-199**）。
  - **native → Java**（`WindowInfosListener` 回调把 SF 的 `gui::WindowInfo` 变成 Java `InputWindowHandle`）：`android_view_InputWindowHandle_fromWindowInfo()` 只写 token/name/frame/…/windowToken/alpha 等（**同文件:223-301**），**完全不写** `touchableRegionSurfaceControl`。所以监听结果里该字段永远 `null`。
- `gui::WindowInfo` 的 Parcel 确实会把 crop handle 当 strong binder 写出去（**frameworks/native/libs/gui/WindowInfo.cpp:170**），但 Java 路径不反序列化它，shell 拿不到 raw WindowInfo parcel。
- 用途层面：crop 字段是“触摸区域裁剪”用的，只有窗口显式调用 `setTouchableRegionCrop` 才非空；普通 Activity 窗口与 `SurfaceView` 不会设置（旧探针实测手机 Steam 窗口 `crop=null`，**android_hardware_input_InputWindowHandle.cpp** 与本机日志一致）。
- **可行而有用的一点**：同一回调里的 `getWindowToken()` 给出的是 `IWindow` Binder（**InputWindowHandle.java:272-278**，JNI 写 `windowToken`：**…InputWindowHandle.cpp:294-295**），这正是问题二通道需要的 token；旧探针已用它成功执行 `IWindow.executeCommand`。但它不是 SurfaceControl。

结论：**不可行（相机子层）**；`WindowInfosListener` 的价值在 IWindow token，不在图层句柄。
权限：`ACCESS_SURFACE_FLINGER`（`WindowInfosListener.java:60`；Shell manifest:199 已声明，旧探针实测可注册成功）。
预期失败信号：结果句柄 crop 恒 null；若强行把它当 SurfaceControl 使用会 NPE/`getLayerId` 抛异常。
验证方式：监听回调打印 `touchableRegionSurfaceControl.get()`，对 Steam/Bilibili 窗口应全为 null（P3）。

#### B. `IActivityTaskManager` / `IWindowOrganizerController.applySyncTransaction` 回调

- 调用序列（shell 反射，rc23 探针与 rc24 已实现）：
  1. `atm = ActivityTaskManager.getService()`（`android.app.ActivityTaskManager` 静态方法）。
  2. `organizer = atm.getWindowOrganizerController()`（`IActivityTaskManager` 隐藏方法，返回 `IWindowOrganizerController`）。
  3. `wct = new android.window.WindowContainerTransaction()`；`wct.setBounds(taskToken, new Rect(bounds))` 等。
  4. 自建 Binder 实现 `android.window.IWindowContainerTransactionCallback`（descriptor 同名），`onTransact` 第一事务码里 `enforceInterface` 后 `data.readInt()`（syncId）再 `data.readTypedObject(SurfaceControl.Transaction.CREATOR)` 得 Transaction，然后 `t.apply(); t.close()`（必须 apply，否则 WM 侧等待）；参考 rc24 `NativeAlphaScene.rebind()`（**NativeAlphaScene.java:154-171**）与 rc23 `TransactionBufferProbe.task()`（**TransactionBufferProbe.java:56-71**）。
  5. `organizer.applySyncTransaction(wct, callbackProxy)`。
- 权限：`WindowOrganizerController.applySyncTransaction` 第一行 `enforceTaskPermission("applySyncTransaction()")`（**WindowOrganizerController.java:253**），其定义为 `MANAGE_ACTIVITY_TASKS`（或已废弃的 `MANAGE_ACTIVITY_STACKS`）（**ActivityTaskManagerService.java:3400-3413**）。Shell manifest 声明了 `MANAGE_ACTIVITY_TASKS`（**Shell/AndroidManifest.xml:272**；core/res/AndroidManifest.xml 中其保护级为 `signature|recents`，同一文件的 `ACCESS_SURFACE_FLINGER` 为 `signature`，见 :6545；shell 为系统侧 uid 2000 应用，设备上旧探针实际调用成功，见下）。
- **能拿到哪些 layer handle**：回调 Transaction 由 `BLASTSyncEngine.finishNow()` 生成：`merged = mWm.mTransactionFactory.get()`（WM 自己的 Transaction），合并 `mOrphanTransaction` 与各 `WindowContainer.mSyncTransaction`（**BLASTSyncEngine.java:219-291**；`WindowContainer.java:313,324,3565-3578` 的 `finishSync` 把容器事务 merge 进 merged），最后 `mListener.onTransactionReady(mSyncId, merged)`（:291）→ `WindowOrganizerController.onTransactionReady`（:2323-2339）→ 回调。因此回调里出现的 SurfaceControl 只可能是 **WM 管理的 WindowContainer 层**：
  - 窗口根：`WindowStateAnimator.createSurfaceLocked()` 创建的 window BLAST layer（`.setName(attrs.getTitle())`，**WindowStateAnimator.java:293-336**）；
  - Task/ActivityRecord 等容器层。
  - **不包含**应用在进程内创建的子层：`ViewRootImpl.updateAndGetBoundsLayer()` 的 `"Bounds for - " + title` 容器层（**ViewRootImpl.java:2792-2804**）、`SurfaceView` 的相机 BLAST 层与 BLAST 子层（**SurfaceView.java:1573-1607**）。
- **设备已证实**（旧日志 `run-task-ui-0-com.valvesoftware.android.steam.community-1.log`）：dumpsys 得到 `root=56109 bounds=56114`；回调 Parcel 只有 `LayerHandle layer=56108`、`LayerHandle layer=56109`，没有 56114；探针在要求“root+bounds 双句柄”时抛 `exact root/bounds handles missing`（:19）。这同时证明：**窗口根句柄能拿到（56109），Bounds 子层句柄拿不到（56114）**；并不是权限问题。
- 预期失败信号：缺 `MANAGE_ACTIVITY_TASKS` → `SecurityException: ... requires android.permission.MANAGE_ACTIVITY_TASKS`；回调事务中目标层句柄缺失（如旧日志的 “exact root/bounds handles missing”）；把 layer id 当句柄用会在 `wrap()` 或 `getLayerId()` 时报 `surface_identity_mismatch`/异常。
- 验证方式：P3 复跑回调 + 与 perfetto 图层树对照，明确“回调层集合 ⊆ WM 容器层”。

#### C. `TransitionInfo` / `Change#getLeash()` 与 `registerTransitionPlayer`

- 协议：实现 `android.window.ITransitionPlayer`（**ITransitionPlayer.aidl:41-66**，`oneway`），`onTransitionReady(IBinder transitionToken, TransitionInfo info, SurfaceControl.Transaction t, SurfaceControl.Transaction finishT)`；`TransitionInfo` 是 Parcelable，内含每条 `Change` 的 `SurfaceControl mLeash`（**TransitionInfo.java:636,923,1007-1011**）、`Root#getLeash()`（:1506-1521），甚至 `getSnapshot()`（:973）。理论上可作为“句柄来源”。
- 权限链：`IWindowOrganizerController.registerTransitionPlayer(ITransitionPlayer)` → `enforceTaskPermission("registerTransitionPlayer()")`（**WindowOrganizerController.java:2342-2356**）→ `TransitionController.registerTransitionPlayer` 无额外 uid 校验（**TransitionController.java:334-348**）。也就是说**权限上 shell 能满足**（与 applySyncTransaction 同一权限）。
- 但**后果严重**：`TransitionController.moveToCollecting()` 依赖 `mTransitionPlayers`，后注册者成为 `getTransitionPlayer()` 返回的“当前播放器”（:315-325, :380-386）。SystemUI 已注册；shell 再注册会**顶替 SystemUI 成为转场播放器**，所有窗口转场等待 shell 回调；shell 不按协议 `startTransition/finishTransition` 会导致转场超时、动画卡顿/中断（`CHANGE_TIMEOUT_MS`/`DEFAULT_TIMEOUT_MS`，:326-329）。这不是“只读监听”，是**劫持系统转场**。
- 收益：即使成功，leash 仍是 **WindowContainer 层**（窗口根/容器），**不包含**应用子层；对“排除相机子层”的 Q1 目标**无增益**。
- 结论：**不建议采用**（源码证实“权限上可能可行”，但风险/收益比极差；不把它写进产品候选）。
- 预期失败信号：`SecurityException`（无权限）；注册后系统转场卡住/超时日志；`TransitionInfo` 里 Change 的 leash 对应窗口根而非相机层。
- 验证方式：仅在 P3 里可做“注册→立刻注销”的最小验证并观察是否影响用户操作，默认不做。

#### D. `SurfaceControl` / `LayerHandle` Parcelable 与隐藏 JNI

- Java API 清单核查（`SurfaceControl.java`，抓取件 221 KB）：
  - `private static native long nativeGetHandle(long nativeObject)`（:282），只在 `assignNativeObject()` 里 `mNativeHandle = nativeGetHandle(nativeObject)`（:1004）；`mNativeHandle` 仅用于 `equals`/`Choreographer.getInstanceForSurfaceControl`（:1631,1673），**不是**可用于构造新 SurfaceControl 的“句柄 API”。
  - `SurfaceControl.mirrorSurface(SurfaceControl mirrorOf)`（:2772-2778）→ native `nativeMirrorSurface`（**android_view_SurfaceControl.cpp:2076-2083**），语义是“对**已存在的 SurfaceControl 对象**建立镜像层级”，不是由 layer id 反查。
  - `public int getLayerId()`（:5370）单向：对象→id。
  - **不存在** `getChildren()`/`getLayerHandle()`/`fromLayerHandle()`/按 id 构造的公开或隐藏方法（对抓取的全文件检索：仅 `nativeGetHandle`、`mirrorSurface`、`getLayerId` 命中；Lead 的初查与此一致）。
  - `Builder.setParent(SurfaceControl parent)`（:1338）与 `Transaction.reparent(sc, newParent)`（:3839）存在，但只能把**自己的**新层/已有对象挂到另一个**已有 SurfaceControl 对象**下——它们不能把 layer id 变成对象，native `SurfaceControl` 也没有面向 Java 的 children 枚举接口。
  - `private SurfaceControl(Parcel in)`（:1525）是私有构造；`CREATOR`（:1715）走 `readFromParcel`，而 `readFromParcel` 依赖 native 反序列化出 **client + handle + layerId**（**native_SurfaceControl.cpp:251-279**）。rc24 `NativeAlphaScene.wrap(IBinder handle, int id)`（**NativeAlphaScene.java:146-153**）正是利用 Parcelable 布局把真实 handle+id 拼进模板：**只有已经拿到 handle binder 时才有意义**。
- native 侧：`SurfaceControl::getHandle()`/`getLayerId()`（**native_SurfaceControl.cpp:182-190**）是 C++ 对象方法；Java 没有跨进程“查询句柄”的 JNI。
- SurfaceFlinger 侧校验：`captureLayers` 根 handle 无效 → “captureLayers called with an invalid or removed parent”（**SurfaceFlinger.cpp:7562-7564**）；exclude handle 无效 → “Invalid layer handle passed as excludeLayer to captureLayers”（:7590-7595）；`LayerHandle::fromIBinder` 若 descriptor 不符 → “handle does not have a valid descriptor”（**LayerHandle.cpp:37-49**）。
- 结论：**不可行**；shell 能“包装”句柄，但无来源。
- 预期失败信号：伪造 binder → SF 日志 + capture 返回 null/`ScreenshotHardwareBuffer` 失败；`wrap()` 后 `getLayerId()` 不匹配 → rc24 的 `surface_identity_mismatch`。

#### E. `SurfaceComposerClient` 客户端 API

- frameworks/base 里没有暴露给 App/Shell 的 Java `SurfaceComposerClient`；客户端只有 `android.view.SurfaceControl`（含 Transaction/Builder）、隐藏的 `SurfaceSession` 等。没有“枚举/查询他人 layer children”的 API。
- `dumpsys SurfaceFlinger` 与 perfetto 的 layer snapshot 只有 `id/name/parent/relative/uid/z` 等元数据（rc24 `NativeAlphaLayers.decode` 的字段映射见 **NativeAlphaLayers.java:14-26**），**不含 handle binder**。
- 结论：**不可行**。

#### F. `ViewRootImpl.getSurfaceControl()` / `SurfaceView.getSurfaceControl()` 的可达性

- 两者都是应用进程内**公开但 @hide** 的方法：`ViewRootImpl.getSurfaceControl()`（**ViewRootImpl.java:12064**）、`SurfaceView.getSurfaceControl()`（**SurfaceView.java:2085-2091**，注释明确“App can only use transactions that don't reparent”）。
- 它们只能由**应用自己**调用；shell 无法跨进程调用（没有 Binder 接口导出这些 Java 对象，`RenderNode`/`SurfaceControl` 都不是可远程调用的对象）。
- `ViewDebug.INVOKE_METHOD` 远程命令：`invokeViewMethod()` 用 `targetView.getClass().getMethod(methodName, argTypes)` 反射调用，参数只支持有限的**基本类型**序列化（`deserializeMethodParameters`，**ViewDebug.java:1879-1918**），返回也会被 `serializeReturnValue` 序列化为基本类型（void/primitive），**无法传入/返回 `SurfaceControl`、`RenderNode`、`ScrollCaptureCallback` 等对象**。rc24 `NativeAlphaProbe.set()` 只用 `F/Z/I` 三种类型（**NativeAlphaProbe.java:117-122**）即受此限制。
- 因此“让应用替我们调用 `ViewRootImpl.getSurfaceControl()` 并把对象带回来”需要应用侧配合或注入，均被约束禁止。
- 结论：**不可行**。

#### G. `dumpsys SurfaceFlinger` / perfetto

- 只有图层 id/name/父子/uid，可作为**身份对照**（判断哪些句柄被回调交出、哪些层存在），不能作为句柄来源。
- 结论：**仅诊断**。

#### H. 唯一的结构性例外：相机在独立应用窗口

- 如果某应用的相机预览不是 Activity 窗口内的 `SurfaceView` 子层，而是**独立窗口**（`PopupWindow`/overlay/独立 `SurfaceControlViewHost` 等），则它会有自己的 `WindowState` BLAST 层（**WindowStateAnimator.java:293-336**），其句柄可能随 WM 同步事务/转场交给 shell（通道 1）。此时：
  - `captureLayers(UI 窗口根)` 本来就不包含相机（不在同一窗口子树）；
  - 或 `captureDisplay` + `setExcludeLayers(相机窗口层句柄)` 可排除。
- 但普通相机扫码/预览页（Steam、微信等）都是本窗口内 `SurfaceView`；**该例外需要真实应用窗口结构验证**，不能外推。
- 结论：**待验证（结构依赖）**，不改变主结论。

### 1.3 问题一结论

- **对“Activity 窗口内 SurfaceView 相机”的通用场景：不可行。** shell 的可达域止于 WM WindowContainer 层；应用进程内创建的 `SurfaceView`/Bounds 等子层句柄无任何合法出口。
- 可实现的替代（按优先级）：
  1. **不排除相机，改用应用内 RenderNode 回放**（问题二），其输出天然不含相机 buffer、只保留 UI 的透明洞 → 这是当前唯一“无相机 + 真 alpha”的通用方向。
  2. 若相机在独立窗口：用 WM 回调句柄排除（H，待验证）。
  3. `captureLayers` 仍是“合成后”数据，不能用于 alpha 判定（旧轮已证）。
- 工程上仍值得保留的能力：rc24 已有“从回调拿 WindowState 句柄 + `wrap()` + `captureLayers`”的实现（**NativeAlphaScene.java:141-171**），P3 可验证其可用性；一旦未来某路径能泄漏子层句柄，`setExcludeLayers` 可立即接上（但要先用自有层验证排除语义，见 P3）。

## 2. 问题二：把 UI 原生重绘连续导出到自有 Surface

### 2.1 协议全链路（调用方 = shell；目标 = 应用窗口）

AOSP16 的 scroll capture 协议由三部分组成：请求/响应（IWindow）、连接（IScrollCaptureConnection）、回调（IScrollCaptureCallbacks）。

**(1) 取得目标窗口的 IWindow token（已实测可行）**
- `WindowInfosListenerForTest`（`@TestApi`，**WindowInfosListenerForTest.java:42-48,198-228**，内部 `WindowInfosListener` 用 SurfaceFlinger 的 window infos；shell manifest 具备 `ACCESS_SURFACE_FLINGER`：Shell/AndroidManifest.xml:199）→ 回调 `InputWindowHandle[]`（`InputWindowHandle.java:272-278` 的 `getWindowToken()` 即 IWindow Binder）。
- 旧探针 `NativeAlphaProbe.rawWindows()`/`select()` 已用它筛选窗口（**NativeAlphaProbe.java:69-100**），设备实测可用。

**(2) 直连 `IWindow.requestScrollCapture`（关键：绕开 WMS 权限）**
- `IWindow.aidl` 是 `oneway interface IWindow`（:44），方法 `void requestScrollCapture(in IScrollCaptureResponseListener callbacks)`（:126）。
- 应用侧实现：`ViewRootImpl.W.requestScrollCapture()` 直接 `viewAncestor.dispatchScrollCaptureRequest(listener)`（**ViewRootImpl.java:11961-11967**），**没有任何权限/uid 检查**（对比同处 `executeCommand` 要求 `DUMP`：:11875-11885）。
- 系统正规入口 `WindowManagerService.requestScrollCapture()` 要求 `READ_FRAME_BUFFER`（**WindowManagerService.java:7479-7481**），并由 WMS 选目标窗口后转给 `targetWindow.mClient.requestScrollCapture(listener)`（:7498-7510）。shell 既然能直接拿 IWindow token，就**不需要走 WMS**。
- 反射调用式（shell）：
  ```
  Object iwindow = Class.forName("android.view.IWindow$Stub")
        .getMethod("asInterface", IBinder.class).invoke(null, windowToken);
  Object listener = /* 自建 Binder，attachInterface(null,"android.view.IScrollCaptureResponseListener")，onTransact 读 ScrollCaptureResponse */;
  iwindow.getClass().getMethod("requestScrollCapture",
        Class.forName("android.view.IScrollCaptureResponseListener")).invoke(iwindow, listener);
  ```
  自建 Binder 的做法与 rc24 的 `IWindowContainerTransactionCallback` 完全同型（**NativeAlphaScene.java:157-164**），只是 descriptor/事务码不同；`ScrollCaptureResponse` 有公开 `CREATOR` 可 `createFromParcel`（**ScrollCaptureResponse.java:223-264**，`writeToParcel` 会在 :208 `writeStrongInterface(mConnection)`）。
- 该“对 `IWindow$Stub.asInterface()` 返回的 Proxy 用 `getClass().getMethod(...)` 反射调用”的模式与 rc24 `WindowProbe.command()`（**WindowProbe.java:24-56**，对 `IWindow.executeCommand`）完全一致；后者已在设备上实测可用，因此本通道的调用式具备先例。

**(3) 响应的内容与分支**
- 应用侧：`ViewRootImpl.handleScrollCaptureRequest()`（**ViewRootImpl.java:11521-11553**）新建 `ScrollCaptureSearchResults`，`collectRootScrollCaptureTargets()`（:11480-11490，窗口级 callback）后向视图树 `dispatchScrollCaptureSearch`（:11546）。
- 完成后 `dispatchScrollCaptureSearchResponse`（:11556-11623）：
  - 无 root view → description “The root view disappeared!”（:11572-11579）；
  - **没有可选 target → description “No scrollable targets found in window”**（:11582-11589）；
  - 有 target → description “Connected”，并填 `boundsInWindow`（:11594-11600）、`windowBounds`（:11602-11607），最后创建 **`ScrollCaptureConnection`**（应用内对象，`IScrollCaptureConnection.Stub`）放进 response（:11610-11616）。
- `ScrollCaptureResponse` 字段/可 parcel 内容见 **ScrollCaptureResponse.java:31-80,194-264**：description / connection / windowBounds / boundsInWindow / windowTitle / packageName / messages。
- shell 侧判定：`response.isConnected()`（:65-68）为 true 才有 connection；`getBoundsInWindow()` 是**滚动内容在窗口坐标系里的可见滚动区域**，后续请求坐标以它为边界。

**(4) 连接与“自带 Surface”帧回放**
- `IScrollCaptureConnection`（**IScrollCaptureConnection.aidl:30-62**）：
  - `ICancellationSignal startCapture(in Surface surface, IScrollCaptureCallbacks callbacks)`（:40）
  - `ICancellationSignal requestImage(in Rect captureArea)`（:50）
  - `ICancellationSignal endCapture()`（:57）；`oneway void close()`（:62）
- 应用侧实现 `ScrollCaptureConnection`（**ScrollCaptureConnection.java:100-168,189-222**）：
  - `startCapture` 校验 `surface.isValid()`（:109-111），`mSession = new ScrollCaptureSession(surface, mScrollBounds, mPositionInWindow)`（:118），在 UI 线程回调 `mLocal.onScrollCaptureStart(session, cancellation, listener)`（:120-127）→ 完成后回调客户 `onCaptureStarted()`（:132-146）。
  - `requestImage(Rect)`：`checkActive()`（未 start 抛 “Not started!”，:279-285），在 UI 线程 `mLocal.onScrollCaptureImageRequest(session, cancellation, rect, listener)`（:150-168）→ 完成回调 `onImageRequestCompleted(0, capturedArea)`（:171-185）。**空 Rect = 本次失败**（语义见 IScrollCaptureCallbacks.aidl:35-43）。
  - `endCapture()` → `onScrollCaptureEnd` → `onCaptureEnded()` → close（:189-222）。
  - **全程无 uid/权限校验**（只校验 Surface 有效、连接处于 active）——这是 shell 可以调用的源码依据。
- 回调接口 `IScrollCaptureCallbacks`（**IScrollCaptureCallbacks.aidl:28-49**，`oneway`）：事务码按声明顺序 1=`onCaptureStarted()`、2=`onImageRequestCompleted(int flags, in Rect capturedArea)`、3=`onCaptureEnded()`（AIDL 语义，调用方自建 Binder 需按此实现 `onTransact`）。
- Surface 由**调用方创建**：shell 可用 `ImageReader.newInstance(w, h, PixelFormat.RGBA_8888, 4, usage)` 的 Surface（rc23 `holeLab` 已验证 shell 进程内 `HardwareRenderer` + ImageReader 可拿到 alpha 精确数据，**run-hole-lab.log:1-3、lab.log:1-3**）；usage 至少需要 `USAGE_GPU_COLOR_OUTPUT | USAGE_GPU_SAMPLED_IMAGE | USAGE_CPU_READ_OFTEN`。

### 2.2 应用侧回放实现与像素语义（决定“有没有相机、有没有 alpha”）

- 目标选中后，`ScrollCaptureViewSupport`（`com.android.internal.view`，**ScrollCaptureViewSupport.java**）实现回放：
  - `onScrollCaptureStart`：`mRenderer.setSurface(session.getSurface())`（:230-233）；`ViewRenderer` 构造时 `mRenderer.setOpaque(false)`（:333-341，**显式透明**，注释 “TODO: Figure out a way to flip this on when we are sure the source window is opaque”——即回放器固定按透明处理）。
  - `onScrollCaptureImageRequest` → `mViewHelper.onScrollRequested(...)`（:237-255）→ `onScrollResult` 里 `view.postOnAnimationDelayed(() -> doCapture(...), mPostScrollDelayMillis)`（:257-278）→ `doCapture` 调 `mRenderer.renderView(view, viewCaptureArea)`（:280-292）。
  - `ViewRenderer.updateRootNode()`（:379-393）：`rootView = source.getRootView()`；`rootView.updateDisplayListIfDirty()`；把**整棵根视图的 display list** `canvas.drawRenderNode(rootViewRenderNode)` 画进一个尺寸=请求区域（`mTempRect`）的 capture RenderNode，`canvas.translate(-mTempRect.left, -mTempRect.top)` 做窗口坐标裁剪；`renderView()` 用 `FrameRenderRequest.syncAndDraw()`（:396-405）产出一帧 buffer。
  - **结论 a（Lead 已核）**：输出是“整窗 UI 重绘在请求矩形内的裁剪”，不是只画滚动子视图；`SurfaceView` 在 display list 里只有透明洞 op（`canvas.punchHole(...)`，见下），**不含相机 buffer**。
  - **结论 b**：请求矩形受 target 的 `scrollBounds` 限制，超出部分返回空 `capturedArea`；因此**一次会话最多拿到 target 覆盖的那块窗口区域**（target 全屏时即整窗）。
  - **结论 c**：帧率 = `requestImage` 往返率（调用方驱动，不是应用持续推流）；每次请求走应用 UI 线程 + `postOnAnimationDelayed`，默认延迟来自 `Settings.Global "screenshot.scroll_capture_delay"`，**默认 60 ms**（:59-60,77-79）→ 理论上限约 16 fps，加上渲染/回传实际更低；该 setting shell 可改但属全局用户设置，探针需还原。
  - **结论 d**：无可见可滚动 target → 无 connection（硬门槛，见 §2.3）。

**洞（Alpha）来源**：`SurfaceView.draw()/dispatchDraw()` 在“非 Z-top 且已 draw 完成”时调 `clearSurfaceViewPort(canvas)`（**SurfaceView.java:630-678**），最终 `canvas.punchHole(0,0,getWidth(),getHeight(),0,0,alpha)`（:728-747）。该 op 进入窗口 display list → scroll-capture 回放或 ViewDebug 重绘都会保留透明洞。rc23 的自有 renderer 洞实验（`below-alpha1 a0=1920 a128=384 a255=1792`）证明同一套 HWUI 语义在 shell 自建 renderer 中也成立（**run-hole-lab.log:1-3**）；**跨进程由应用 renderer 回放**仍待 P1 实测。

**副作用/限制**：
- `onPrepareForStart` 会临时关滚动条/overscroll（`ScrollViewCaptureHelper.java:54-64`），结束时恢复（:185-193）；`onScrollRequested` 可能为把请求区域带到可见范围而**滚动容器**（`contentView.requestRectangleOnScreen(input, true)`，**ScrollViewCaptureHelper.java:137-153**），请求“当前可见区域”时通常不产生滚动，但**必须实测确认**（P1）。
- 连接是“会话级”的：`endCapture`/`close` 后需重新 `requestScrollCapture`（`ScrollCaptureConnection.java:189-258`；`ScrollCaptureViewSupport.onScrollCaptureEnd` 会 `mRenderer.destroy()`，:294-306）。
- 请求需要在 UI 线程之外以 Binder 回调驱动；`requestImage` 会取消上一个 pending 操作（`cancelPendingAction`，:260-267），**调用方必须串行等待回调**，否则会丢帧。

### 2.3 硬门槛：没有滚动目标 = 完全不可用

- target 生成规则：`View.dispatchScrollCaptureSearch` → `View.onScrollCaptureSearch`（**View.java:33262-33294**）：优先用应用显式设置的 `mListenerInfo.mScrollCaptureCallback`；否则 `createScrollCaptureCallbackInternal` → `ScrollCaptureInternal.requestCallback()`（**View.java:33227-33232**）。
- `ScrollCaptureInternal.requestCallback` 只对 `detectScrollingType(view)` 非 `TYPE_FIXED` 的 View 返回 callback（**ScrollCaptureInternal.java:164-213**）；`TYPE_FIXED` 的判据是 `!(view.canScrollVertically(DOWN) || view.canScrollVertically(UP))`（:78-86）。即：**窗口内必须有当前可垂直滚动的可见 View**（`ViewGroup` 还需满足子 View/scrollY 等启发式），否则整棵树一个 target 都不会产生。
- `ScrollCaptureSearchResults.getTopResult()` 还会过滤“被其它滚动视图遮挡”的 target（`scrollCaptureTargetZOrderFix` 分支，**ScrollCaptureSearchResults.java:152-203**），并优先 `SCROLL_CAPTURE_HINT_INCLUDE`、后代、大区域（:242-286）。
- 设备实测（上一轮）：Steam 扫一扫、微信扫一扫均报“无可滚动目标”（旧结论文件 `调研_合成前UI原生Alpha_20261031.md:108`）；这就是固定相机页的硬门槛。
- **绕过评估（本轮结论）**：
  - `ViewRootImpl.addScrollCaptureCallback()`（**ViewRootImpl.java:11444-11449**）只能在应用进程内调用；shell 无法注入。
  - `ViewDebug.INVOKE_METHOD` 不能传 `ScrollCaptureCallback` 对象，也不能把返回对象带回（§1.2 F），无法远程注册；`View.setScrollCaptureCallback` 同样是应用侧 API。
  - 没有“给固定窗口注册根级 callback”的远程命令/系统接口；`ViewDebug.startRenderingCommandsCapture` 无远程入口（§2.4）。
  - 因此：**对没有任何可滚动 View 的页面，框架级 scroll capture 不可用**，不存在 shell 侧合法绕过（除应用自身实现 `onScrollCaptureSearch`/`setScrollCaptureCallback` 这种需应用配合的情况）。
- 有利的一面：**任何**可见的滚动容器都能成为 target（哪怕很小）。若页面里恰好有列表（如 Steam 主页/商店、Bilibili 首页），就能用它当“整窗重绘驱动器”，请求矩形取该容器的当前可见区域（不滚动）即可持续取到该区域的 UI 重绘（含洞）。

### 2.4 `ViewDebug` 远程命令面（能力与边界）

入口：`IWindow.executeCommand(String command, String parameters, ParcelFileDescriptor out)`（**IWindow.aidl:56**）；应用侧 `ViewRootImpl.W.executeCommand` 要求调用者持有 `DUMP` 权限（**ViewRootImpl.java:11875-11885**；shell manifest 声明 DUMP：Shell/AndroidManifest.xml:164；旧探针实测对 debuggable=false 应用可用），然后 `ViewDebug.dispatchCommand(view, command, parameters, clientStream)`（:11890）。

命令与能力（**ViewDebug.java:424-437,543-572**）：

| 命令 | 行为 | 是否像素 | 边界/代价 |
|---|---|---|---|
| `DUMP` | 文本视图树（含每个 View 的 `类名@hash`、属性、alpha 等） | 否 | 用于拿根 View id 给 CAPTURE；文本很大（旧探针用 8 MB 上限） |
| `DUMP_THEME` | 主题属性转储 | 否 | 用于判断 `windowActivityTransitions` 等 |
| `DUMP_ENCODED` | ViewHierarchyEncoder 二进制/文本 | 否 | 诊断 |
| `CAPTURE <viewId>` | 对指定 View 做**硬件/软件重绘**到 Bitmap，再 `Bitmap.compress(PNG,100)` 写 pipe | **是（PNG）** | 旧实测 1440×3200 编码+传输 360.9 ms、189 273 B；重绘保留洞与半透明（positive），无预览时全不透明（paused 对照）。实现：**ViewDebug.java:1099-1129,1132-1159** |
| `CAPTURE_LAYERS` | 写 display frame 尺寸 + 递归每个 View 的 PNG（`performViewCapture(view,true)` + PNG） | 是（多段 PNG） | 比 CAPTURE 更慢；二进制流格式见 **ViewDebug.java:765-831** |
| `INVALIDATE` / `REQUEST_LAYOUT` | 触发重绘/重布局 | 否 | 有 UI 副作用，探针避免频用 |
| `OUTPUT_DISPLAYLIST <viewId>` | `ViewRootImpl.outputDisplayList` → `RenderNode.output()`（原生调试输出） | 否 | **ViewRootImpl.java:5275-5277**；不是像素导出 |
| `PROFILE <viewId>` | 用 RenderNode 做绘制耗时分析 | 否 | 诊断 |
| `INVOKE_METHOD <viewId> <method> <base64 args>` | UI 线程反射调用 View 的 public 方法 | 否 | 参数/返回仅基本类型（**ViewDebug.java:1879-1918**）；rc24 用它做 `setAlpha/setZOrderOnTop/setBackgroundColor`（NativeAlphaProbe.java:117-122） |

**为什么只能 PNG**：`CAPTURE` 路径固定为 `performViewCapture()`（`createSnapshot(Hardware/SoftwareCanvasProvider, ...)`）→ `Bitmap.compress(PNG,100)` → `OutputStream`（**ViewDebug.java:1107-1129**）；协议里没有“raw buffer/共享内存/直接写入调用方 Surface”的选项。`CAPTURE_LAYERS` 同样逐 View PNG。**`startRenderingCommandsCapture` 虽是“渲染命令流”（`Picture.writeToStream`，**ViewDebug.java:1036**），但它是公开静态 API、只能在应用进程内调用；`dispatchCommand` 的命令表中没有对应远程命令（§2.4 表），所以 shell 不可达**；即便可达，跨进程 Picture 的版本兼容性也不适合作为生产通道。

### 2.5 其它可能入口（评估过、不采用）

| 入口 | 结论 | 依据 |
|---|---|---|
| Layout Inspector 的 rendering-commands capture | 走进程内 agent/`startRenderingCommandsCapture`，需调试/注入；shell 无入口 | ViewDebug.java:1082 起；命令表无此项 |
| `SurfaceControl.captureLayers`（含 display） | 合成后像素，相机已被合成进去（不透明） | §3；ScreenCapture.java:105-176 |
| `SurfaceControl.mirrorSurface` / `mirrorDisplay`（rc24 现方案） | 同样合成后；rc24 的 `NativeAlphaProbe.capture()` 走的正是 `captureLayers`（**NativeAlphaProbe.java:287-296**） | 旧轮已实测全 255 |
| MediaProjection / VirtualDisplay / screencap | 合成后 + 用户授权 | — |
| `PixelCopy` | 只能对自家 SurfaceView 取图 | 应用侧 API |
| Accessibility / UiAutomation 截图 | 合成后 | — |
| 自家 `HardwareRenderer.setOpaque(false)` | 证明“透明重放器 + 洞语义”可行（已实测），但只渲染自家 RenderNode，不是目标应用 UI | run-hole-lab.log；HardwareRenderer.java:626 |

### 2.6 排序：shell 端可达到的“UI 原始 Alpha”帧率路径

| 排名 | 路径 | 理论/实测帧率 | Alpha 保真 | 是否含相机 | 前提/风险 |
|---|---|---|---|---|---|
| 1 | **ScrollCapture 连接 + 自有 Surface 回放**（P1 待实测） | 调用方驱动；默认 ≥60 ms/帧（≈≤16 fps）受 setting 与 UI 线程渲染限制，实际预计 5-15 fps | 预期保真（RenderNode 重绘 + `setOpaque(false)`；洞来自 `punchHole`） | 否（SurfaceView 只有洞 op） | 必须有可滚动 target；会话级、需串行请求；可能触发滚动/滚动条变化（可恢复）；需设备实测 |
| 2 | `ViewDebug CAPTURE` PNG（已实测） | 360.9 ms/帧 ≈ 2.8 fps（1440×3200） | 已实测保真（A=0/部分/255 三档 + paused 全 255 对照） | 否（洞保留） | 仅 DUMP 权限；PNG 编解码成本；无滚动页也可用；非实时 |
| 3 | `ViewDebug CAPTURE_LAYERS` | 比 2 更慢（逐 View PNG） | 预期保真 | 否 | 诊断用，不建议生产 |
| — | `captureLayers`/`mirrorDisplay`/screencap/MediaProjection | 高（合成帧率） | **否**（全不透明） | 是 | 合成后数据 |
| — | `startRenderingCommandsCapture` | 不可达 | — | — | 无远程入口 |

**结论**：若目标是“桌面相机叠手机原生 UI Alpha”的实时通道，**优先级 1 = ScrollCapture→自有 Surface（仅当目标页有滚动容器）**；否则只能退到 `CAPTURE` PNG（~2.8 fps，仅诊断/慢速兜底），或维持“逐应用规则 + 视觉近似”的现有 Engine 路线。

## 3. 问题三：原始 UI GraphicBuffer / BufferData —— 同步事务是否带像素

### 3.1 机制链：为什么 WM 同步事务不带 buffer（确认上一轮结论）

1. **回调事务由 WM 自己创建**：`BLASTSyncEngine.SyncGroup.finishNow()` 里 `SurfaceControl.Transaction merged = mWm.mTransactionFactory.get()`（**BLASTSyncEngine.java:224**）；只 merge `mOrphanTransaction`（:225-227）和同步集合内各 `WindowContainer.finishSync(merged, ...)`（:275-278）。`WindowContainer.finishSync` 的内容是 `outMergedTransaction.merge(mSyncTransaction)`（**WindowContainer.java:3565-3578**），而 `mSyncTransaction` 是 WM 的 `mTransactionFactory` 创建的**图层状态事务**（**WindowContainer.java:313,324**），里面是 show/hide/位置/alpha/crop/layer 等 `layer_state_t` 元数据（如 **WindowState.java:766-767,5056-5065,5312** 的 setPosition/setFrameRate/setLayer）。
2. **应用像素走另一条路**：应用进程 `ViewRootImpl.registerCallbacksForSync()` 里 `mBlastBufferQueue.syncNextTransaction(transaction -> surfaceSyncGroup.addTransaction(transaction))`（**ViewRootImpl.java:12878-12983**），这个 transaction 里才有 `setBuffer`；`BLASTBufferQueue` 的 native 实现在应用进程内 `t->setBuffer(mSurfaceControl, buffer, fence, frameNumber, ...)` 并 `apply(...)` 给 SF（**frameworks/native/libs/gui/BLASTBufferQueue.cpp:653,712,826**；Java 接口 **BLASTBufferQueue.java:96-121,167-177**）。WM 只通过 BLAST sync 引擎等待“该窗口的 buffer 已提交”（`wc.isSyncFinished()`，**BLASTSyncEngine.java:197-217**），**不接收 buffer 本体**。
3. **事务序列化只在有 BufferData 时才写 buffer**：`layer_state_t` 的 `what & eBufferChanged` 时才写 `bufferData`（**LayerState.cpp:218-221**）；`BufferData::writeToParcel` 只有 `buffer != nullptr` 才 `output->write(*buffer)`（**LayerState.cpp:1035-1044**，GraphicBuffer 的标准 Parcel + FD）。WM 的 merged transaction 从不 setBuffer → 没有 BufferData → 没有 FD/GraphicBuffer。
4. **BufferCache 的存在不改变结论**：`SurfaceComposerClient::Transaction::writeToParcel` 先 `cacheBuffers()`（**SurfaceComposerClient.cpp:896-908**），命中时“Strip the buffer and send only the id”（:1034-1049）——这是**本来带 buffer 的事务**的优化，不适用于 WM 元数据事务；旧探针观察到的“无 buffer 变更位/fds=false”不是缓存导致的丢失（探针还做了反序列化后再次写出检查，旧结论已述）。
5. **BLAST sync 回调语义**：`IWindowContainerTransactionCallback.onTransactionReady(int syncId, SurfaceControl.Transaction t)` 的 `t` 就是步骤 1 的 merged（**WindowOrganizerController.java:2323-2339**），也解释了为什么旧探针在回调里只能拿到图层 handle/元数据。

### 3.2 设备证据（上一轮，非本轮新跑）

- `steam-physical-same-bounds.log`:1-22：每次同步事务 `PARCEL bytes=3692 fds=false rawBuffers=0`；反序列化后重写 `bytes=3564 fds=false rawBuffers=0`。
- `run-task-draw-0-...-2.log`:1-34：附加空 bounds-change transaction 触发下一次绘制后，仍然 `fds=false rawBuffers=0`。
- `run-watch-...log`:3-132：新任务启动/Splash→主窗口 8 次回调，全部无 buffer。
- `run-task-ui-...-1.log`:2-19：回调中只有 LayerHandle 56108/56109（图层信息），`what=0x80100000` 等，无 `eBufferChanged=0x00200000`。
- `verified-summary.json`:55-66：`windowSync.rawBuffersObserved=0`、`rootOnlyCapture.boundsBinderObtained=false`。
- 自有缓冲区对照（证明“带 buffer 的事务确实能读出像素”）：`lab.log`:1-3（64×64、RGBA、A8 直方图精确）；因此并非探针不会读，而是目标事务里没有 buffer。

### 3.3 “除 captureLayers 外是否还有合法取得应用 UI 图层像素的路径”分类

| 类别 | 路径 | 数据性质 | 是否跨进程可用 | 结论 |
|---|---|---|---|---|
| 合成后 | `ScreenCapture.captureLayers/captureDisplay`（SF 按图层树重新合成，**ScreenCapture.java:105-176**；排除层在 SF 内按 id 过滤，**LayerSnapshotBuilder.cpp:733**）、`screencap`、MediaProjection、`mirrorDisplay`（rc24） | 已合成像素（相机已不透明） | 是（需对应权限） | 不能给原生 UI Alpha |
| 合成前·应用重绘 | ScrollCapture 回放（§2）、`ViewDebug CAPTURE` PNG（§2.4） | 应用 HWUI/Skia 重绘的 UI（含洞/半透明） | 是（需应用侧接口，非注入） | **唯一 alpha 保真来源**；前者按请求帧，后者 ~2.8 fps |
| 统计/元数据 | `SurfaceControl.getDisplayedContentSample(displayToken,maxFrames,timestamp)` 返回 `DisplayedContentSample`（颜色直方图/采样，**SurfaceControl.java:2125-2130**；SF 侧 `getDisplayedContentSample`：**ISurfaceComposer.aidl:334**，结果类型 **DisplayedFrameStats.aidl**）、`dumpsys gfxinfo/SurfaceFlinger` 统计、FrameStats | 直方图/统计值，**不含像素** | 是（需 ACCESS_SURFACE_FLINGER 等） | 不能重建 UI/Alpha |
| 自有缓冲区 | `SurfaceControl.Transaction.setBuffer`/`BLASTBufferQueue` 只对**自家** layer 有效；无跨进程 `getActiveBuffer` Java API | 自家像素 | 否 | 仅用于本机渲染/回放 |
| 进程内对象 | `RenderNode`/`HardwareRenderer`/`Picture` 均不可 Parcelable（设备 `actual-apis.log`:20-21 `RenderNode parcelable=false`） | — | 否 | 不能作为跨进程导出口 |

**结论**：`captureLayers` 是唯一“系统级、跨进程、可编程取像素”的合法路径，但它是**合成后**数据；要“合成前 UI Alpha”，AOSP 只提供**应用内重绘**类通道（scroll capture / ViewDebug 重绘），不存在“直接拿应用 UI 图层 GraphicBuffer”的合法 API。旧轮“读事务 BufferData”方向对自有缓冲区可行，对目标应用事务不可行（本节的机制解释）。

## 4. 问题四：给 probe-device 的 3 个具体探针实验（与他们 A/B/C/D 互补）

> 以下实验均假定：shell uid 2000 `app_process`、不装 APK、不注入、不点击/启停应用；所有自建 Surface/Renderer/ImageReader 用完释放；任何全局 setting 修改必须 finally 还原；探针只读目标应用，不做 View 属性修改（INVOKE_METHOD 写操作留给 rc24 现有路径，不属本轮）。
> 与 task-2 的 A/B/C/D 分工：A（CAPTURE 直方图/耗时）、B（CAPTURE_LAYERS）、C（requestScrollCapture 基础）、D（句柄/排除语义）。下面 P1 是 **C 的“协议+自有 Surface 帧流”深化**，P2 是 **A 的“阳性/阴性对照 + 无滚动页”补强**，P3 是 **D 的“句柄面/事务 buffer/排除机制”补强**；不重复 A/B 的基础统计，只补 AOSP 结论所依赖的关键断言。

### P1（最高优先）：ScrollCapture 连接 → startCapture → requestImage 帧流实测
- **目标**：验证 §2.1-2.2 的“自有 Surface + 应用侧 RenderNode 回放”是否真的产出**跨进程 UI 原生 Alpha**（含 SurfaceView 洞）、帧率、裁剪语义；优先用**有滚动容器的页面**（平板 Bilibili 首页/详情页、手机 Steam 主页），不要用相机扫码页。
- **调用**（成功则记录完整反射依据）：
  1. WindowInfosListener 取目标窗口 IWindow token（旧 `NativeAlphaProbe.select()`/`rawWindows()` 可直接复用）。
  2. 自建 `IScrollCaptureResponseListener` Binder（descriptor `android.view.IScrollCaptureResponseListener`，事务码 1；`data.enforceInterface` 后 `ScrollCaptureResponse.CREATOR.createFromParcel(data)`），`IWindow.requestScrollCapture(listenerProxy)`。
  3. 打印 response：`description/windowTitle/packageName/boundsInWindow/windowBounds/isConnected/messages`；预期 `description="Connected"`。
  4. 建 `ImageReader`（尺寸=（boundsInWindow.width, height）或窗口尺寸两种都试；`PixelFormat.RGBA_8888`；maxImages=4；usage=GPU_COLOR_OUTPUT|GPU_SAMPLED_IMAGE|CPU_READ_OFTEN）。
  5. 用反射调 `connection.startCapture(surface, callbacksProxy)`；callbacks 自建 Binder（descriptor `android.view.IScrollCaptureCallbacks`；码 1/2/3 对应 onCaptureStarted/onImageRequestCompleted/onCaptureEnded），等待 onCaptureStarted。
  6. 串行循环 `requestImage(new Rect(0,0,boundsInWindow.width(),boundsInWindow.height()))` 20 次，每次等码 2 回调后再发下一次；`acquireLatestImage()` 读 A8 直方图/尺寸/耗时，记录空 capturedArea 次数、回调 flags。
  7. 结束 `endCapture()`/`close()`；记录会话期间目标容器 `getScrollY` 变化（用 DUMP 前后对比或 CAPTURE 前后像素对比）。
- **预期证据**：onCaptureStarted 到达；onImageRequestCompleted 的 capturedArea 非空；ImageReader 帧 A8 有三档（0/中间/255），洞区域 A=0；帧尺寸=请求区域尺寸；单帧延迟（请求→回调→可读）≈60ms+渲染；`fds`/buffer 与“是否 RGBA8888”。
- **终止条件**：3 次 `requestImage` 都空 capturedArea → 记录失败退出；窗口 token 失效/页面切换 → 中止；onCaptureEnded 或 5 s 无回调超时 → 释放并记录；出现目标应用可见滚动/界面跳变且无法恢复 → 立即 endCapture 并中止。
- **额外断言（重要）**：① 表面尺寸取“窗口大小”时是否被裁剪/缩放（对比两种尺寸输出的尺寸/内容）；② 连续同 rect 请求的帧 CRC 是否稳定（无相机页应基本稳定，除动画）；③ 对比 `screenshot.scroll_capture_delay` 默认/0（改后还原）对帧率影响；④ 结束后目标滚动位置是否恢复（`ScrollViewCaptureHelper.onPrepareForEnd` 恢复机制，**ScrollViewCaptureHelper.java:185-193**）。

### P2：固定相机页阴性 + CAPTURE PNG 兜底复测
- **目标**：把“Steam 扫一扫（无滚动 target）”的失败信号固定成可回归证据，同时给出 CAPTURE PNG 兜底的真实预算与 Alpha 对照；对应 AOSP §2.3/§2.4。
- **调用**：
  1. 对手机 Steam 扫一扫页（用户打开、有相机预览）直连 `IWindow.requestScrollCapture`；打印 response 全文与 messages（预期 description 含 “No scrollable targets found in window”，`isConnected=false`）。
  2. 同页取根 View id（DUMP 解析 `com.android.internal.policy.DecorView@<hash>`），连发 5 次 `CAPTURE <rootId>`（每次独立 pipe），记录 PNG 字节数、耗时、A8 三档计数；再请用户暂停预览/离开相机页后重复 3 次做阴性对照（预期洞消失、A255 增多）。
  3. （可选）若同应用存在可滚动页面，对其做一次 requestScrollCapture 记录“Connected”与 boundsInWindow，作为阳性对照证明协议实现正确。
- **预期证据**：阴性页稳定返回“无可滚动目标”；CAPTURE 在相机预览存在时出现 A=0 洞（旧实测 3 195 023 个 A=0）、暂停后全 A=255；耗时/字节数分布（旧：360.9 ms / 189 273 B）。
- **终止条件**：连续 3 次 CAPTURE 超时/失败 → 记录设备差异并停；用户离开目标页 → 中止；若固定页意外出现 scroll target（说明应用版本差异）→ 立即记录并转入 P1。
- **产物**：`precompose-ui-20261031/` 下 `scrollcapture-negative-*.log`、`capture-fallback-*.log` 与 summary JSON 片段。

### P3：句柄面 + 排除语义 + 事务 buffer 三项复核
- **目标**：把 §1.2 B/D、§3.2 的结论在设备上一次性钉死，给 Lead 一个可验收的“不可行/机制可用”证据包。
- **调用**：
  1. 权限面：`dumpsys package com.android.shell` 过滤 `READ_FRAME_BUFFER`、`MANAGE_ACTIVITY_TASKS`、`ACCESS_SURFACE_FLINGER` 是否 granted（佐证 shell 通道前提；失败则记录“未授权”，不阻塞）。
  2. 句柄面：复用旧 `TransactionBufferProbe.task(..., ui=true)` 路径——对 Steam/Bilibili 当前任务 `applySyncTransaction(setBounds)`，在回调 Parcel 中收集全部 `LayerHandle`（旧方法 `layerHandles()`/`binders()`），同时用 perfetto layer snapshot 打印该任务的图层树（id/name/parent/uid）。断言：回调中**只有窗口根或容器层**，**没有**“`... SurfaceView[...]#id`”或“`Bounds for - <window>#id`”层；把回调拿到的窗口根 handle 用 `wrap()` 包成 SurfaceControl 并 `captureLayers` 一次，确认该句柄可用（预期画面=包含相机的合成图）。
  3. 排除语义：建自有层树（container + 两个 BLAST 子层，其中一个画红/一个画蓝且 alpha 不同），对 parent 做 `captureLayers`：不排除 vs `setExcludeLayers([childA])` vs `setExcludeLayers([伪造/错配 handle])`；读帧直方图与 SF logcat（预期：排除子层 A 后其区域透明/消失；错配 handle 触发“Invalid layer handle passed as excludeLayer to captureLayers”，**SurfaceFlinger.cpp:7590-7595**）。
  4. 事务 buffer：任一回调 Parcel 打印 `fds`/扫描 GraphicBuffer 签名（旧 `scan()` 逻辑），预期 `fds=false rawBuffers=0`；作为 §3.1 机制链的设备端补证。
- **预期证据**：权限 granted 清单；回调 layer id 集合与 perfetto 层树对照表（证明“可达域=WM 容器层”）；自有层 exclude 前后差异（证明 `setExcludeLayers` 机制本身可用，缺的只是子层句柄）；回调 fds=false。
- **终止条件**：回调 3 次超时/无回调 → 记录失败退出；layer 对照出现“回调含相机层”这一反例 → 立即上报（推翻 Q1 主结论的唯一可能）；自建层测试导致 SF 异常 → 立即销毁层并退出。
- **注意**：`setBounds` 尺寸变化要做 finally 恢复（旧探针已做，`RESIZE_RESTORED`）；不要触碰 app 页面状态。

## 5. 风险、未决与建议

### 5.1 未决/待验证清单
1. **ScrollCapture 回放能否跨进程产出真实 Alpha 与洞**：源码强支持、机制自洽；**必须由 P1 实测**（本文件标“理论可行/待验证”）。
2. **表面尺寸语义**（窗口尺寸 vs `boundsInWindow` 尺寸）与裁剪/缩放行为：P1 断言①。
3. **会话期间滚动副作用**是否可接受/可恢复：P1 断言③④。
4. **固定相机页是否有其它滚动容器**：P2；有则可作为“重绘驱动器”，无则此路对相机页不可用。
5. **`setExcludeLayers` 在自有层上的真实语义**（是否递归排除子层、是否保留父层孔洞）：P3。
6. **设备实际 API level/厂商差异**：AOSP16 为参考；设备 `IWindow.requestScrollCapture` 已由反射清单确认存在（`actual-apis.log`:19），但 scroll capture 的具体实现/延迟/`Settings` 行为以设备为准；`dumpsys package com.android.shell` 权限清单由 P3 佐证。
7. **独立窗口相机**的结构性例外：需要真实应用图层树验证（P3 观察即可，不专门设计实验）。

### 5.2 风险
- **ScrollCapture 会短暂接管目标窗口的滚动/滚动条状态**（`ScrollViewCaptureHelper.onPrepareForStart/onScrollRequested`，**ScrollViewCaptureHelper.java:54-64,66-153**），即使不滚动，也可能让用户看到滚动条消失/恢复；频繁 start/end 会增加应用 UI 线程负载；需产品侧限定频率/时长，并确保 `endCapture` 一定执行。
- **`registerTransitionPlayer` 是系统级接管**（§1.2 C），严禁作为“句柄监听”手段进入产品。
- **`ViewDebug CAPTURE` 每次都会让应用做一次整窗重绘+PNG 编码**（旧实测 360 ms/帧），高频调用会显著占用目标应用 UI 线程，只适合诊断或 <3 fps 兜底。
- **不可把“回调收到窗口根句柄”误当作“能排除相机”**：`captureLayers` 仍会合成相机子树。

### 5.3 建议给 Lead 的产品结论
1. 不要再把 `setExcludeLayers` 作为通用相机分离方案投入（除非出现“相机在独立窗口”的结构证据）；rc24 现有 `NativeAlphaScene` 的窗口句柄获取/包装能力可保留备用。
2. 把“ScrollCapture→自有 Surface”列为**唯一值得设备实测的实时原生 Alpha 通道**，以 task-2 的 C + 本文件 P1 为验收；验收标准：真机连续 ≥20 帧、A8 三档、洞区域 A=0、帧率/延迟数据、页面状态可恢复。
3. 固定相机页（无滚动容器）预期不可用：产品上仍走现有 Engine 规则 + 诊断 PNG，不要为此扩大应用白名单；等 P2 结果再决定。
4. Q3 方向（直接读应用 UI GraphicBuffer）**关闭**；后续投入集中到 Q2 与“相机在独立窗口”的结构探测。
