# 内部渲染器研究：整页 GPU alpha

**2026-10-30 性能更新：** 原生 alpha 已实际经无线 ADB 传到电脑，差分流约 66.9 包/秒、57.3 次/秒新画面变化、0.92 MB/s，532 帧原生 CRC 一致。完整 RGBA 软件合成约 30/s。见 [吞吐上限实测](原生Alpha吞吐上限实测_20261030.md)。本文下述尚未完成传输的表述属于前期阶段，真实 Windows 窗口呈现和与 RGB 视频同步仍未接入。

日期：2026-10-29。对象：小米平板 25091RP04C / Android 16 / 微信 com.tencent.mm。目标是得到可透视叠加的整页逐像素 alpha，不要求单独导出每个控件。

## 本轮结论

已经在平板的独立实验进程中复现并验证：窗口曾经画满不透明背景后，如果 HardwareRenderer 保持 opaque=true，移除背景仍可能得到全 A=255；对同一个 HardwareRenderer 调用 setOpaque(false)，即可重新得到正确透明底和半透明图形。

后续更新：已通过 Activity 场景过渡找到跨进程入口，独立实验 APK 实际验证了 renderer opaque 的 true→false→true；真实微信也取得了整页原生 alpha 像素及电脑端透明预览。**重复稳定性仍未通过，部分实验微信主动退出。** 详细成功/失败记录和限制见 [场景过渡原生Alpha实测记录](场景过渡原生Alpha实测记录.md)。下文保留前期机制调查，不能将其当作后续尚无跨进程入口的结论。

## 1. opaque=true 的准确含义

HardwareRenderer.java 的说明和 SkiaPipeline.cpp 的实际实现一致：

- opaque=false：每帧绘制前清到透明。
- opaque=true：应用承担画满输出的责任，渲染器可以省略透明清屏。

它不是“把每个像素的 alpha 强制改成 255”的同义词。

最初对照使用一个新建的固定 RGBA ImageReader Surface，仅绘制半透明矩形。在 opaque=true 下也观察到了透明底；后续帧出现叠加累积。这纠正了将 opaque=true 简化为“硬性抹掉 alpha”的理解。

## 2. 复现旧不透明缓冲残留

实现：RendererResearch.java → lab()。独立进程 UID=2000，不挂接微信进程。输出为 576×1280 RGBA ImageReader，像素直接从 Image.Plane 读取；没有 PNG 生成、压缩或传输。

绘制内容：左侧三分之一为 alpha=128 的蓝色矩形，其余区域为空。总像素数 737,280。

| 阶段 | 实际操作 | 像素结果 |
| --- | --- | --- |
| 0–5 | opaque=true，先画满黑底，再画半透明矩形 | 全部 737,280 像素 A=255 |
| 6–8 | 同一个 renderer，移除黑底，保持 opaque=true | 仍全部 A=255；RGB hash 随叠加改变 |
| 9–11 | 同一个 renderer、同一 Surface、同一矩形，改 opaque=false | 每帧 A=0 为 491,520，A=128 为 245,760，A=255 为 0 |

最后三帧的 RGBA hash 完全一致：ff5fda6205e32325。由此确认透明清屏确实消除了旧目标像素的影响，并且结果没有依赖背景颜色反推。

日志：tablet-wechat/renderer-lab.log。最早的“新 RGBA 缓冲”对照保存在同模式 .previous 日志中。

日志中的 requestMs 仅是 syncAndDraw 调用耗时，不能当作端到端延迟；本轮没有做实时视频链路或 60fps 验收。

## 3. 微信实际状态与进程边界

通过系统包信息确认：

- 微信 FLAG_DEBUGGABLE=false。
- isProfileableByShell=false。
- SurfaceFlinger 的分配记录中，BaseScanUI 缓冲申请 req fmt=1，即 RGBA8888，并非仅 RGBX 的存储格式。此为缓冲分配记录，不等于已直接映射当前生产者缓冲。

在本机实际 framework 上枚举接口，确认存在：

- View.getThreadedRenderer()。
- HardwareRenderer.setOpaque(boolean)、isOpaque()。
- WindowManagerGlobal.changeCanvasOpacity(IBinder, boolean)。

但这些对象/方法是进程内能力。WindowManagerGlobal.changeCanvasOpacity 遍历的是调用进程自己的 mParams/mRoots；在 shell 进程中调用它，不能修改微信进程里的 ViewRootImpl。

IWindow 的 INVOKE_METHOD 调试接口只能以 View 为目标，参数支持基本类型、String 和 byte[]，不支持对象链。getThreadedRenderer() 即使执行，其返回对象也不会被导出为可继续调用的远程对象；AOSP ViewDebug.serializeReturnValue 对此类返回值写出的是 SIG_VOID。它与 Binder 代理不是一回事。

因此，“shell 可以反射调用隐藏 API”并不等于“shell 已能拿到另一个进程里的 HardwareRenderer Java 对象”。本轮没有尝试解除微信的调试限制、替换安装或变更其数据。

实际接口及属性日志：tablet-wechat/renderer-api.log。

## 4. 系统提供的独立透明渲染路径：ScrollCapture

源码中找到 ScrollCaptureViewSupport.ViewRenderer：它会创建独立 HardwareRenderer，明确 setOpaque(false)，并重绘 rootView 的 RenderNode 到调用方提供的 Surface。这个路径可以无需 PNG，而不仅是截取已经合成的窗口。

新增 inspect-scroll，通过 IWindow.requestScrollCapture 按正常协议请求微信扫一扫。

实际结果：

```text
description = No scrollable targets found in window
connection = null
packageName = com.tencent.mm
windowTitle = com.tencent.mm/com.tencent.mm.plugin.scanner.ui.BaseScanUI
```

所以当前扫描页没有建立可用的重绘连接。本轮不能把这个入口算作扫描页成功方案；它仍值得用于本身支持 ScrollCapture 的页面研究。

INCLUDE 提示只影响目标选择，不会自动给普通不可滚动 View 安装重绘回调；本轮没有用任意 UI 改动来伪造滚动目标。

日志：tablet-wechat/inspect-scroll.log。实现包含正常连接的 startCapture/requestImage/endCapture/close，以及原始 RGBA 接收；本轮连接为空，接收分支未在微信上执行。

## 5. 微信页面容器静态检查

只读复制安装包并分析 FrostedContentView。它的公开方法能设置模糊半径、上下模糊区域和 frostedEnabled。实现通过 RenderNode 和 RenderEffect 绘制上下区域；在该容器中未发现直接调用 setOpaque 或 changeCanvasOpacity 的桥接。

没有盲调混淆方法，没有修改或重新安装微信。此处只覆盖已检查的容器，不能外推为整个微信绝无其他入口。

证据：tablet-wechat/FrostedContentView.smali；原始安装包副本 wechat-base-analysis.apk。使用 Android SDK 自带 apkanalyzer 只读分析。

## 6. 其他候选接口

### 内建 SKP 捕获

Properties.cpp 对文件式 SKP 捕获设有 debuggingEnabled 条件。SkiaPipeline.cpp 的单帧序列化还会调用 SkPngEncoder 编码其中的图像。它不能直接视为符合当前目标的“免 PNG、实时原始 alpha 通道”。本轮仅核查源码，没有开启系统 SKP 属性。

### 小米扩展

本机 IWindowManager 暴露 miCaptureLayers(int,String) 和 captureSpecialLayers(String)。已从本机 services.jar 核查实现：

- captureSpecialLayers 的 String 参数没有用于筛选窗口，实际捕获顶部焦点 Activity。因此没有调用此接口，以免误采其他前台应用。
- miCaptureLayers 接受 captureMode=3，按包名筛选可见任务，最终仍调用 ScreenCapture.captureLayers，附带小米 capture mode。不是应用内 HardwareRenderer 对象的远程控制接口。

早期目标不可见时三次调用返回 null，未用作 alpha 不可用的证据。随后在有效虚拟屏中完成三次真实采集，均为 576×1280、737,280 像素全部 A=255；捕获调用约 27.98 / 14.45 / 9.84 ms。这组是在透明渲染入口打通前的基线，不能外推为打通后仍无法保留 alpha。

证据：tablet-wechat/WindowManagerService-device.smali；tablet-wechat/miui-capture.log。没有调用忽略包名的 captureSpecialLayers。

```powershell
python build_wechat_probe.py
# 以下两项在平板独立进程里运行，不要求微信仍在该 display；参数须为正数。
python run_wechat_probe.py renderer-lab 149
```

所有 runner 仍限定平板型号和已授权的无线序列号，使用 ADB 5038。上述是前期入口，不能把旧显示屏号 149 当作当前微信位置。后续场景过渡模式会自行创建临时虚拟屏，具体命令见更新记录。rc20 构建目录未修改。

## 后续研究应针对的具体缺口

跨进程场景过渡入口已经取得实际像素证据；接下来应隔离微信主动退出的生命周期条件，验证多次和长时间运行，再研究 HardwareBuffer 的实时传输与 Windows 合成。单独修改合成器 OPAQUE 标记、Window 的 format、sRGB 设置，仍不等价于改变应用内部渲染状态。

当前成功样本已经同时隐藏相机并清除实色底，取得真实微信整页 UI 的逐像素 alpha；除完整的 8 帧读取外，后续还通过了“先等待初始化 15 秒、过渡后观察约 33 秒、文字 alpha 主动隐藏/恢复”的验证，见 [初始化假说验证](初始化假说_延时与主动重绘验证.md)。此前的重复退出尚未解决。应区分“原生 alpha 已取得”与“生产实时链路可用”，不能把成功样本当作 rc20 已完成接入。
