# 原生 alpha 吞吐：捕获、读取、压缩、ADB 传输及电脑合成

日期：2026-10-30。对象仍为已授权的小米平板 25091RP04C / Android 16 / 微信 `com.tencent.mm`。免 root、ADB shell UID 2000；独立研究程序，没有修改微信安装包或 rc20。

## 结论

本次不设达标刷新率，测量的是各阶段实际能处理多少数据，以及其中有多少是新画面。当前 **576×1280、无线 ADB** 条件下：

- 捕获 API 可以反复返回约 **255–393 次/秒**，但多数情况下是在重复捕获同一源画面。这不是有效界面帧率。
- 微信当前扫一扫动画实际约 **60 次/秒有效变化**；虚拟屏虽然已请求并获得 144Hz，不能据此认为微信产生了 144 个不同画面。
- 无损 alpha 全帧传到电脑约 **53–54 包/秒**。无损 XOR 差分后约 **66.9 包/秒、57.3 次/秒有效变化**，532 帧全部重建 CRC 校验通过，带宽约 **0.92 MB/s**。
- 整张 RGBA 都走无损 CPU 压缩、传输和电脑软件合成，最终约 **30–31 次/秒**。其瓶颈不能归结为 alpha 无法读取。

因此，当前最有价值的结果是：**真实原生 alpha 已能持续、无损送到电脑，差分通道接近本页源内容更新速率。** 这里找到了当前原型的实测速率和主要瓶颈，尚不能称为设备的绝对硬件上限，也没有完成 rc20 的真实窗口呈现或 RGB 视频与 alpha 同步接入。

## 条件与测法

实验捕获 576×1280 原生 UI；相机隐藏、实色底清除，微信自己的渲染器持续绘制。先等扫一扫初始化 15 秒，再启用透明渲染。整个基准会话持续约一分钟以上的渲染/读取负载。

物理屏当时活动模式约 120Hz、最高支持约 144Hz。基准虚拟屏请求最高支持值，实际返回 **144.00002Hz**，避免默认虚拟屏 60Hz 成为人为限制。未修改物理屏刷新率设置。

每个本地阶段预热 1 秒，测量 6 秒；负载结束的捕获复测为 5 秒。每种网络流测量约 8 秒，电脑继续接收至数据全部处理完成。逐帧打印、直方图、PNG 编码均不在这些持续循环内。PNG 仅在电脑端保存最后一帧预览。

捕获结果为 HardwareBuffer；CPU 路径通过硬件 Bitmap 拷贝和 `copyPixelsToBuffer` 得到原生预乘 RGBA，实测字节顺序为 RGBA、alpha 位于第 4 字节。已通过实际颜色像素和 alpha 抽样校验。此路径不需要先反预乘或按底色反算 alpha。

## 分阶段结果

下表来自最终一次完整会话，另两轮基线保存于证据目录。数值有负载、时钟及阶段顺序波动，不能将各阶段相加或把最快一次当作长期保证。

| 阶段 | 处理/调用次数每秒 | 捕获到不同像素画面的次数每秒 | 说明 |
| --- | ---: | ---: | --- |
| 只捕获并释放 HardwareBuffer | 264.1 | 未读取像素，不计 | 不含 CPU 读回和传输 |
| 捕获、CPU RGBA 读回及 CRC | 73.4 | 59.9 | 显示本页有效变化约 60/s |
| 捕获、读回、alpha 全帧压缩 | 55.0 | 53.6 | zlib level 1，约 118 KB/帧 |
| 捕获、读回、整张 RGBA 压缩 | 47.3 | 47.2 | 约 244 KB/帧 |
| 捕获、读回、alpha XOR 差分压缩 | 59.1 | 55.6 | 本地阶段约 15 KB/帧 |
| 负载后仅捕获缓冲 | 393.5 | 未读取像素，不计 | 5 秒连续观测；不是 393 个新画面 |

前两次成功会话的纯捕获测得约 298、271、255 次/秒等结果，说明该项存在明显波动，不能以单次调用耗时倒数宣布固定上限。

SurfaceControl 的内容帧统计快照约为 **58–62 次呈现记录/秒**，而较快 CPU 读取阶段观察到约 60 次/秒不同像素内容。这些是本页、此设备策略下的结果，不代表其他页面或应用的上限。

## 实际无线 ADB 传输

使用独立 ADB 5038 的临时端口转发，设备端仅监听回环地址。每帧带顺序编号、长度、阶段耗时和原生数据 CRC。TCP 数据在电脑端解压并检查编号和 CRC。测试结束删除本次建立的端口转发。

| 接收路径 | 电脑处理包数/秒 | 有效像素变化/秒 | 有效负载 MB/s | 完整校验帧数 |
| --- | ---: | ---: | ---: | ---: |
| 完整 RGBA 无损流＋Pillow 离屏合成 | 29.94 | 29.94 | 7.32 | 311 / 311 |
| alpha 全帧无损流 | 54.21 | 49.95 | 6.44 | 433 / 433 |
| alpha XOR 差分无损流 | **66.85** | **57.30** | **0.919** | **532 / 532** |

三个流共 **1,276 帧 CRC 全部一致**。alpha 差分的 532 包中，456 次相邻内容发生变化、76 次重复；重复包没有算成新画面。差分保留原生 alpha 的全部 8 位值，没有降低分辨率、量化阈值或有损编码。

“无损”指已经捕获的帧保留原始 alpha 值，不代表源画面每一帧都已采到。约 57 次有效变化与源内容约 60 次变化之间仍有差距。

### 差分具体做了什么

首帧以全零 alpha 为参考：`delta = currentAlpha XOR previousAlpha`，然后压缩 delta。电脑解压后与上一帧再次 XOR，恢复当前原生 alpha。首帧相当于完整关键帧，随后大部分静态控件和遮罩变成零，仅扫描动画变化区域留下非零数据。

单包约从 119 KB 降到 14 KB。由于包率也提高，实际带宽从 6.44 MB/s 降到 0.919 MB/s，约下降 **86%**。还原后逐帧 CRC 与手机当前原生 alpha 一致。

这是 alpha 通道的性能，不是完整视频加透明度的窗口呈现速率。生产实现还需周期关键帧、断线恢复，以及与 RGB 视频使用同一帧编号/时间戳；本实验采用可靠 TCP 顺序传输，不模拟丢包恢复。

## 瓶颈与较慢帧

最终差分流的手机端每帧耗时：

| 手机步骤 | 中位数 | P95 | P99 |
| --- | ---: | ---: | ---: |
| captureLayers 调用 | 3.37 ms | 4.68 ms | 5.65 ms |
| GPU 结果读回 CPU | 6.11 ms | 11.03 ms | 15.06 ms |
| alpha 提取、差分压缩及 CRC | 3.78 ms | 6.71 ms | 8.14 ms |

这些中位数不能直接相加倒算成可靠速率，尾部抖动会错过源画面。差分后带宽已较小，**CPU 读回和软件处理**是下一步更值得测量优化的部分。GPU 直接处理或只读回 alpha 平面可能提高余量，但未在本次实现，不能把其收益写成已达到。

完整 RGBA 的电脑端 zlib 解压/校验中位约 9.48 ms、反预乘/软件合成约 20.20 ms。手机约 8.07 秒产生 311 帧，电脑处理完约需 10.39 秒，存在末尾积压。不能用手机发送的 38.5 包/秒代替电脑实际处理的 29.94 次/秒。

还试了直接预乘公式的 NumPy 实现：图像与基线最多只差 1 个颜色量化级，但该实现中位约 31.9 ms，反而更慢，整链路约 22.7/s。最终保留较快的 Pillow 基线；不能只按算法表达更直接便假定性能更好。

电脑结果为**收到、解码并离屏合成**，没有提交给真实 Windows 透视窗口，也没有测 DWM 实际呈现时间。两端时钟未同步，不能从此数据声明单向端到端延迟。

## 稳定性与清理

三次成功基准会话结束时均验证恢复后的整页 A=255，并正常关闭原 BaseScanUI，释放虚拟屏。最终一次基准开始与结束仍有正常逐像素 alpha。

仍有进入实验虚拟屏失败的记录，包括 LauncherUI 窗口失效或微信任务消失，发生在进入扫一扫、修改 alpha 或执行场景过渡之前。不能将这些失败一概认定为 alpha 读取失败或外挂检测；入口迁移和应用生命周期稳定性仍未解决。
