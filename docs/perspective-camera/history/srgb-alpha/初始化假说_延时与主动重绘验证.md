# “只能在初始化前 8 帧读到 alpha”假说验证

日期：2026-10-29。平板微信 `com.tencent.mm`，Android 16，ADB shell / 免 root。实验虚拟屏 170，576×1280、120 dpi。未修改 rc20。

## 结果

**本轮结果不支持“只能在扫一扫初始化的前几帧得到 alpha”。** 微信扫一扫正常运行 15 秒后才开始修改渲染状态；过渡完成 31.7 秒后仍有原生逐像素 alpha，并在约 33 秒时通过局部主动重绘验证了 alpha 会随新画面变化。

原先的“8 帧”是 8 次主动抽样，相邻约 120 ms，不是微信从启动开始渲染的第 1–8 帧。此前的短时取样不能排除初始化，因此这次专门延长了时间并加入重绘对照。

## 实验顺序

1. 正常进入扫一扫，保留相机和原背景，等待 **15 秒**。之后重新读取实际窗口和 Activity token，保证目标仍是 BaseScanUI。
2. 隐藏相机、清除实色底并改 RGBA 格式，但尚不执行场景过渡。此时两条有效目标图层的基线仍全部 **A=255**。
3. 再执行场景过渡，取得微信自身的协调器并完成协议。
4. 复用同一个实际图层，在过渡完成约 1.7、2.7、6.7、11.7、21.7、31.7 秒时捕获；期间不重复转换、不重启页面。
5. 约 32 秒时选中既有“轻触照亮”文字 View，记录原 alpha=1。仅将此文字 alpha 暂设为 0，然后恢复为 1；没有点击手电筒，也没有调低整窗透明度。
6. 恢复原相机、背景、格式和绘制标志；重新获取当前图层确认整页 A=255，正常返回主页面并确认原扫一扫 Activity 已关闭。释放实验虚拟屏。

所有样本 A=0 均为 0，目标图层整体 alpha 均为 1，flags 均为 8448。渐变遮罩覆盖全页，所以没有完全透明像素。半透明像素数量相同不表示画面没更新：各次 alpha hash 和 RGBA hash 均在变化，像素的空间分布在更新。

本轮捕获调用耗时约 2.5–12.6 ms，存在波动。不能把上一轮的中位 2.56 ms 当作长期固定延迟，也不能把低频抽样当作 60fps 验收。

## 主动重绘对照

以初始文字中 2,499 个明亮像素的位置构成固定观察集合，始终比较相同坐标：

| 阶段 | 过渡后时间 | 该组像素平均 alpha |
| --- | ---: | ---: |
| 原文字 | 32.125 s | 199.735094 |
| 文字 alpha=0 | 32.713 s | 9.193277 |
| 恢复原 alpha=1 | 33.459 s | 199.735094 |

文字隐藏时仍有底部渐变遮罩，所以平均 alpha 降到约 9 而非 0。恢复后准确回到原值。电脑端直接读取两张原始 ARGB 字节，再独立计算同一组坐标，结果与设备端记录完全一致。

这排除了“只是初始缓冲或静态 alpha 快照，后面不能随 UI 更新”的解释。对于本轮所测页面，alpha 在初始化和过渡结束后仍能持续产生并响应实际重绘。

## 尚未回答的问题

这是一轮约 33 秒过渡后观察，不代表数小时、页面切换、多应用或 60fps 流都已稳定。此前部分重复实验中微信主动退出的原因仍未确认，应与“是否仅初始化时可读”分开调查。本轮正常完成取样和清理，没有复现退出。
