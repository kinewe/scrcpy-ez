# RC.18 与 resize8 的继承核查及 flex 修订

2026-10-27，基线提交 `5a27bd847af0486c28d6936e701b3ae962bf383a`，标签 `ez-2.4.2-rc.17-resize8`。

## 核查结果

- layout6：`FlexUiLayout` 逻辑画布与主屏有效 DPI 策略仍在，源码与基线一致
- preview7：Windows 拖动回调消费新帧、按比例重绘、线程和重入保护仍在；`screen.c` 新增校准遮罩，但没有删除这段拖动代码
- resize8：`DisplayResizeDebouncer` 首笔立即执行、100ms 合并和末次尺寸处理仍在，源码与基线一致
- 防省电冻结：`AppPowerSave`、`XiaomiMillet`、`PowerSaveLeaseStore`、共享心跳与续租/恢复代码与基线一致；当前 RC.18 版本名不命中旧详细诊断开关，状态日志频率变低，豁免与续租不受该开关控制
- mDNS：`gui/internal/adb/mdns*.go` 与基线逐文件一致，包含 RC.15 的重复通告唤醒、跨包缓存、排队核验与快速回网调度

## 已确认的 flex 接入缺口

RC.18 首包保留了 native `server.c` 中旧条件：开启透视相机时不发送 `flex_display_preserve_ui=true`。虽然 Java 端已允许透视模式使用 UI 保留路径，客户端仍把入口挡住了。RC.18 默认开启透视，使原本仅作用于旧透视模式的例外成为普通应用默认路径；因此不能用“源文件仍在”证明正式入口已启用新 flex。

本修订移除该相机条件。窗口跟随开启且 GUI 自动 DPI 为真时，普通与透视窗口均发送 UI 保留参数；手动 DPI、关闭 flex、`SCEZ_VD_PRESERVE_UI=0` 的显式回退仍独立保留。主投屏和微信已有的匹配原屏兼容策略不变。此修订没有更改防冻结或 mDNS 策略。

本地测试直接调用实际 `execute_server()` 并拦截最终 adb argv，不连接设备。五种条件通过；重新带入首包旧条件时，透视开启这一例按预期失败，确认该测试能够发现遗漏。构建后协议仍是 `5.0.1-ez2.4.2-rc.18`。

## 本轮设备证据和限制

用户反馈平板完全息屏后，应用窗口仍很快停止响应；不能将问题标记为修复。观察到标准和 MILLET 豁免均为 true，解冻广播返回 0，虚拟屏亮着、心跳未超时；抽样的浏览器主进程和一个隔离渲染进程 `cgroup.events` 均为 `frozen 0`。这些只反映采样时已检查进程的状态，不能排除其他关联进程、厂商机制或渲染/输入路径停止。

本轮另建浏览器对照会话时，系统把同一浏览器任务从用户窗口所在的 display 114 移到了临时 display 115，原显示已没有应用任务。旧窗口留帧与进程冻结不能混为一谈；本轮重复会话不是有效的锁屏修复对照，后续必须使用单一会话复测。临时窗口已经关闭，用户登录数据未清除。

企业微信临时窗口已启动虚拟相机并完成几何及多底色校准，但用户报告方向、位置或布局异常。诊断脚本还缺少 GUI 注入的自动 DPI 环境值，已补齐，尚未用设备重测。因此本轮不能推断 1/10fps 或交错输入是不能扫码的原因，也不能宣称连续桌面输入已解决问题。

设备已由用户带走。修订版 flex 的真实布局效果、锁屏停止响应、企业微信扫码均待回归实测。二维码页和临时投屏已关闭，采样图清理，保留少量文本日志与本地核查记录。
