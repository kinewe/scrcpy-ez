# RC23 规则式自动机制与抽样计划

本轮约束：免 root、无 APK；所有判断围绕当前实际能力、窗口归属与输出证据。应用名、版本、机型、SDK、厂商和 ROM 不作为成功方案的准入名单。版本/签名/设备信息仍是诊断与观察记录。

## 将问题分阶段，而不是按应用打补丁

| 阶段/症状 | 必须取得的证据 | 机制行为 | 抽样 |
|---|---|---|---|
| 未识别相机页 | 当前目标 UID 的相机活动、非主屏窗口、可绑定预览 View/层 | 区分无相机、视图未就绪、没有可分离的相机层、多窗口歧义；不能无限轮询后冒充成功 | V次元作为待诊断案例；先检查框架识别边界 |
| 首次校准后退出/黑屏，重入成功 | 校准、窗口/token/根 View/Activity 的变化顺序、清理行为 | 新旧窗口分代；旧窗口消失后不结束替代页面；不将初始化空缓冲直接认定永久不兼容 | QQ或浏览器选其一 |
| 初始旋转/位置错位 | display rotation、显示与根视图尺寸、预览范围、来源 epoch | 几何变化使旧映射和旧帧失效；尺寸相同的旋转也应识别；未稳定不发布旧合成 | 抖音 |
| 光带累积/特效叠加 | 同一原生缓冲是否已经有痕迹、是否使用原生通道、重建 CRC | 分清应用自身渲染残留、错误来源、旧帧/错误映射；不先用模糊或抠色掩盖 | 抖音；必要时百度网盘二选一 |
| 有透明但帧率低 | 读取后端、色域、逐阶段耗时、变化行比例 | 自动选择 GPU 原生/sRGB 转换、严格验证 A8，失败回退并有限重试；记录实测性能 | 企业微信、小红书（已发现 P3 退回 CPU） |
| 根页/未知背景/共享相机与 UI 层 | 可逆操作、原始层级、是否存在独立 UI、恢复范围 | 没有恢复证明不修改；不能为了透明隐藏整个 GPU UI；失败有具体原因 | 上述样本若覆盖则不另加应用 |
| 正向回归 | 首次、重新进入、页面切换、稳定运行 | 同样的规则与验证，不因曾成功就跳过证据 | 航旅纵横或已稳定微信 |

这张表是假设与取证计划，不把用户观察直接当作已证实根因。不会逐一测试全部列出的应用，也不承诺用同一透明技巧强行支持全部渲染器。

## 匹配规则与观察记录分开

运行时规则身份取页面渲染结构、预览类型、捕获路径、有限操作角色和恢复条件。能力由当前机实际 API、组件、窗口及最终输出确认。旧记录可以作为候选，但不能把串号、ROM、型号、版本差异当作禁止条件，也不能照搬 UID、Binder、View 实例地址或旧坐标。

设备档案中保留观察信息用于追溯。观察记录的存储键可以区分不同设备/版本/几何，它不是规则匹配键。候选去重优先保留不同有效规则，不能让同一设备的重复观察挤掉其他能力方案。历史失败不成为永久禁用规则。

## 进入、恢复、退出的边界

窗口代次、Activity 记录与 ViewRoot 代次不同。Activity token 在配置重建时可能仍属于同一任务；因此仅检查 taskId 不足以证明仍是原窗口。恢复和关闭必须核对原窗口 token、UID、display 及当前存在性。旧窗口已经被替换时，释放自己的捕获/过渡资源，不能结束新窗口。

预览就绪、可见 UI、来源初始化、透明验证分别有界等待。输出失败应先撤销发布、恢复本次修改，不能自动扩大变更范围或跨页面重试。

## 连续读取

同一原生 RGBA 流包括完整帧和无损变化行补丁。Alpha 必须逐字节准确；sRGB 来源保留原预乘像素，P3等来源转到显示用 sRGB 时应与软件色域转换参考比较并记录 RGB 量化误差。颜色转换不应被错误描述为原始 RGBA 全字节不变。

性能记录与透明成功分别入档。记录后端、输入/输出色域、Alpha 精确验证、RGB 误差、采样数、来源新帧率、读取/编码/发送耗时与回退原因。它是现场测量，不是跨设备帧率保证。慢或不支持时保留可解释的状态，不伪报视频帧率为原生 UI 更新率。

## 本轮进展

运行匹配已去掉平台/串号/ROM条件；新增独立 ruleKey，档案键保留环境观察，发送给设备的模板不含设备和应用版本诊断信息。候选按不同成功规则去重，不让设备重复记录挤占。P3 GPU 转 sRGB 路径已在小红书 3200×2136 实测；用户确认更流畅、无残影、返回再进入仍能自动合成。设备读取约 26–32 ms，长时来源速率中位约 16 FPS；首次与重进约 1.94/2.17 秒。严格保持 A8，RGB 色域转换参考的最大量化差为 1。

已加入原窗口存在性与根视图代次检查，避免结束替代窗口；Surface 原层级可读且背景可恢复时可精确恢复，其余仍要求受限的原页面恢复范围。这些生命周期/旋转规则的跨应用实测仍在进行，不能视为用户列出的应用已全部兼容。


## Engine 10：抖音源端累积诊断与待验补救（2026-10-30）

QQ 本轮首次进入正常停留，原生通道建立约 2118ms；这不是所有生命周期问题均已修复的证明。抖音竖屏初次未错位，但持续出现动画累积。日志确认约 22.854s 后相机区域透明覆盖降至 0.59565，触发机制自身关闭原扫描 Activity，并非已证实的应用崩溃。独立只读 CPU 原始合成器截图也出现 Alpha 逐渐不透明，问题在电脑传输之前；不能仅归咎电脑渲染或差分编码。

本轮修正：持续异常至少三样本且 350ms 后再执行恢复；允许全屏、作用域可校验的 SurfaceView 页面使用已有系统场景透明转换补救；档案验证要求 SurfaceView 场景仍有 surfaceOnTop 操作。自有 GPU 目标每次先 CLEAR 再 SRC。原先 -1 层级不能用动态 mediaOverlay setter 保证精确恢复，保守改为需关闭原子 Activity 的恢复范围；未实现 compositionOrder 精确快照。Engine 10 仍须抖音实机验证，尚不能声称累积已解决。

用户要求暂缓进一步帧率优化，优先兼容、生命周期、累积和旋转；用户已接管所有界面操作，研究端只读设备与日志。


Engine 10 实机补救约 495ms 完成系统转换，但在读取源图层前被 scene_layer_identity_missing 中止并恢复原页。只读 dumpsys 确认原因：完整图层清单中的长 Activity 名未截断，而包含 UID 的树形摘要将名字缩为 [...]。旧实现要求同一行同时含完整名字与 UID，对长名称不成立。Engine 11 按图层 ID 连接完整名字清单和 UID 摘要，再与同任务 WCT 返回的句柄取交集；不放宽 UID、任务、窗口令牌检查。新增自检区分同名系统 UID 图层和 SurfaceView 子图层。待重新实机验证。


### Engine 11 抖音实测结果

日志 RC23_RULES_DOUYIN-32555.log，手机 VD136。初始 display-mirror 通道 1897ms 接通，但约 27 秒后检测到持续覆盖退化；系统场景转换 410ms，成功取得 UID/名称/任务交叉校验的应用窗口图层 51210。切换后输入为 sRGB，GPU 逐字节 A8/RGBA 校验通过，未再触发累积恢复。用户确认“干净，正常停留，第二次直接干净合成”。第二次命中能力规则直接使用 window-buffer-layer，转换 295ms、接通 2896ms，随后连续超过五分钟无同类失败。成功步骤已由运行包写入应用档案，engineVersion=11、cameraKind=surface、strategy=system-scene、captureSource=window-buffer-layer。

结论：此次完成的是“SurfaceView 源缓冲累积 + 长图层名匹配失败”这一类补救，未加入抖音包名分支。首轮未知规则仍可能等到持续症状出现；已知成功规则可直接复用。当前只读窗口 format=TRANSPARENT，不能单凭像素格式反推内部渲染器的清帧状态，因此尚未把它加入提前触发的硬条件。不能将本例成功外推为支付宝、米游社、Steam、向日葵、V 次元等全部通过。

后续待查：未知控件类的能力发现、共享 GL 画面无法独立隐藏相机时的拒绝条件、初次旋转与同尺寸旋转映射、合法不透明内容与源端退化的区分、导航到子页面时延后恢复的生命周期。当前恢复范围仍可能要求结束原扫描子 Activity，不能宣称全部退出类问题已修复。

## Engine 12：失败应用只读结构抽样与初始方向

五个应用已在本机原始状态只读采样，均未声明 FLAG_SECURE；不能把蓝底等同于禁屏。具体结果见 docs/handoffs/结果_失败应用结构探测_20261030.md。Steam 存在同名后缀的 React 容器与更深的真正 SurfaceView，候选新增叶节点约束。支付宝/向日葵根背景分别为 StateListDrawable/NinePatchDrawable；Steam/向日葵根 Activity 内扫码，不能直接采用关闭扫描子 Activity 的恢复。V次元新版已经能触发相机，但仅找到全页共享混淆 Surface，未证明可分离，不能隐藏整页假称兼容。

方向：GUI 的自动比例源为横向传输缓存，已增加启动时读取主屏当前逻辑尺寸的意图，通过分连接参数、bat 和原生服务传递；明确比例优先。没有改主屏旋转、没有永久锁定 VD，也没有使用机型/版本准入。新候选 Engine 12 仅解决结构误选、具体失败原因和启动形态，不宣称五应用均已支持。新规则设备端未运行，遵守本轮不推送 DEX/不改属性的边界。

## Engine 15 后续（2026-10-31）

用户复测 Engine 14：支付宝已不再退出，四个应用仍显示纯蓝底。Steam 的扫码页会自行暂停相机预览，并显示点击恢复提示；此时仍在同一页面，不能把相机 Surface 的消失直接归类为应用不兼容。

### 已核实的读取缺口

默认 `dumpsys SurfaceFlinger --proto` 原始数据没有 Steam 虚拟屏窗口的名称字节，解码后也没有目标层。此前“解析器丢弃 Steam 记录”的说法不成立；默认协议快照过滤虚拟显示才是这次层级后备失效的原因。

改用系统 Perfetto 的 `android.surfaceflinger.layers`，配置 `MODE_DUMP`、`TRACE_FLAG_VIRTUAL_DISPLAYS` 与 `TRACE_FLAG_EXTRA`，已通过纯 shell 在当前手机取得单次快照。实际记录包含 UID 10360 的 Steam 窗口，以及原始 z=-2、relative 指向同 UID 应用窗口、parent 经 Bounds 返回该窗口的相机 Surface。其 View 哈希为 931048e，层 ID 55432；这些仅是本次现场值，不进入可移植规则。

生产读取通过标准输入传入短配置，通过独立标准输出接收二进制，丢弃命令的诊断输出；没有安装 APK，不注入应用代码，不开启持续跟踪。解析器支持 Perfetto TracePacket 的字段 93 和旧 LYRTRACE 两种封装。系统不支持该快照时回退旧协议，仍必须取得两次一致且身份完整的目标层才能使用原始层级。

### 新候选路径及边界

新增 `window-direct`：在根 View 尺寸/位置与虚拟屏一致、现有属性可恢复、系统具备同步窗口事务与句柄能力时，借用精确应用窗口的 SurfaceControl，直接读取窗口图层。该分支不启动设置页面，不触发场景透明转换；无效时仍按能力判断是否使用已有 system-scene。每个相机实例有界尝试，失败恢复属性并停留，不反复重试，不将它写为成功。该分支的实际 Alpha 兼容性尚待用户测试，不能视为已修复支付宝等应用。

直接窗口档案必须来自 Engine 15，包含 prepareWindowSource、window-buffer-layer，以及 exact 或有现场证据的 themeResource 恢复策略；不接受 closeScanner 或系统场景元数据。继续由至少两帧原生 A8、空间变化、相机区域透明覆盖检查决定成功，成功后才入档。

主题读取增加容量、独立超时及错误日志，避免把读取失败当作主题没有资源。运行中预览消失记录为 camera_preview_disappeared，不生成“不支持”档案；恢复预览后重新匹配实际 View。

V次元 Engine 14 日志已经有虚拟相机活动与送帧，问题是单个共享渲染 Surface 下的 Alpha 分离。当前未添加隐藏整块共享 UI 的规则，不能宣称已兼容。

### 本轮验证

- 从实际 Perfetto 快照核实 Steam 相机层、UID、祖先链和 z=-2；默认协议对照样本不含该虚拟屏。
- 既有真实支付宝/向日葵资源表解析继续通过。
- Go 档案及应用相关测试 66 项通过；服务端与 GUI 构建完成。
- 三处既有送帧核心文件保持 RC22 基线内容。本轮没有调整 Alpha 帧率。
- 待用户只用新版 Steam 入口恢复预览验证，再据日志推进其余样本。


## Engine 15 现场失败与 Engine 16 收敛（2026-10-31）

Engine 15 的 Steam 实测已完成：两次快照稳定读到实际 SurfaceView 的 z=-2，绑定使用 exact 恢复；直接窗口借用句柄也成功。但 display-mirror、window-direct、system-scene 均未通过原生 Alpha 验证，SUPPORTED 为 0，不能宣称已修复蓝底。

该轮还暴露生命周期缺陷：在 exact 恢复模式下，system-scene 失败后释放整个会话，下一次轮询又对仍存在的同一窗口重试，导致重复场景转换与相机重建。用户已按要求关闭测试窗口。Engine 16 改为恢复属性、仅释放可恢复的窗口/场景句柄，保留 suspended 会话，等待实际页面或预览变化；不因同一失败状态立即重跑补救。同时新增每个失败阶段的 min/max Alpha、透明像素数、相机区域覆盖和实际来源日志。

原始结构中 Steam 的祖先含 CompositeBackgroundDrawable，虽然 drawing:opaque=false，仍不能据此证明相机区域是透明的；它只是非全不透明属性，保留的不透明区域和原生窗口状态都仍需分辨。这是下一步调查线索，不是已证明的根因。本轮没有尝试不可恢复地清除自定义 Drawable，也没有隐藏带有其他 UI 的祖先。

Engine 16 保留已证实的虚拟屏图层读取修复与有界直接窗口候选，仍未验证 Steam Alpha 成功。用户暂时无需再轮测其他应用。


### Engine 16 现场结果（同日）

用户从 RC23_E16_STEAM 进入扫一扫后，日志 RC23_E16_STEAM-17732.log 记录：

- display=163，SurfaceView 原始层级已命中，恢复策略 exact。
- display-mirror、window-direct、system-scene 三阶段均为 minAlpha=255、maxAlpha=255、partial=0、samples=4608000、cameraAlphaCoverage=0，SUPPORTED=0。直接窗口和场景窗口句柄均取得成功，仍然不透明。
- system-scene 仅执行一次，失败后恢复 opacity 并保存一条 unsupported；到约 31 秒后预览消失，没有再次触发场景转换。与 Engine 15 的重复转换问题相比，现场验证已收敛。

因此 Steam 的自暂停确实缩短取证窗口，但不能解释全部蓝底：相机活动期间已读到完整不透明 A8。下一步需区分根背景、自定义 React 背景绘制和窗口合成标志，不应继续通过延长采样或重复场景转换碰运气。当前仍不得写入成功档案。
