# 透视相机研发全记录：rc17 至 rc25

整理日期：2026-11-03。项目：scrcpy-ez／音墨，2.4.2 候选版本系列。

本文整理从 rc17 到 rc25 的透视相机探索，包括成功方案、被撤回的候选、失败对照、性能工作及社区调研。资料来自已有设计文档、实验报告、结果摘要、源码归档和本轮工作记录。重复构建及同条件重试合并叙述，有独立假设或结论的实验分别保留；没有记录支持的环节不补写结果。

本文是研发记录，不是全应用兼容列表，也不是发布说明。历史报告中的“待验证”以其后的有效实测更新；旧报告里过强的否定结论在第十二节集中修正。

## 一、最终留下了什么

到本记录截止时，项目已经获得以下成果：

1. 桌面作为 Android 虚拟相机输入，Windows 本地合成应用 UI 的完整基础链路。
2. 单色键、多底色校准、静态原生 PNG 与实时动态层混合等可以工作的特定场景方案。
3. 部分真实应用页面的连续原生 Alpha 采集、无损 RGBA 差分传输和桌面叠加。
4. 按实际窗口、预览结构和恢复能力适配的规则机制，替代不断增加包名白名单。
5. 小米特定 ROM 上不改目标 View、背景或 Activity 的相机子树名称过滤原型。
6. GPU 读回、色域验证、无损编码、Windows 进程退出等可独立复用的工程修复。
7. 自有进程间共享 RGBA HardwareBuffer，以及导出并跨进程回放 HWUI 绘制指令的底层实证。

**仍未得到的成果：免 root、不修改目标 APK、对任意应用都稳定有效的高速合成前 UI RGBA 获取方案。** 支付宝现有 APTextureView 场景仍没有通过稳定性、完整 UI、持续动态、最终显示与扫码业务的联合验收。

不能把全部探索归结成“没有拿到 RGBA”：若干应用与结构已经成功。也不能把局部成功写成“通用原生透明流已解决”。主要缺口是目标绘制内容的可达性与分离条件。

## 二、问题定义与验收口径

透视相机涉及三个方向：电脑桌面送进虚拟相机，应用产生 UI，电脑把 UI 叠回本地桌面。三者的帧率和成功条件不同。

```text
电脑桌面 → 捕获/编码 → Android 虚拟相机 → 应用识别/预览
                                            ↓
                            应用 UI 与相机的绘制/合成
                                            ↓
                      捕获 → 读回 → 编码/传输 → 电脑重建/叠加
```

本文使用以下口径：

|术语|本文含义|
|---|---|
|RGBA8888|四个 8 位通道的存储格式；整张图的 A 都是 255 仍然是 RGBA|
|原生 Alpha|来自实际绘制/捕获结果的逐像素透明度，不由底色估算，也不靠整窗统一降透明度制造|
|无损传输|电脑重建帧与编码前帧一致；不自动证明捕获源正确、未漏帧或色域转换没有误差|
|持续新帧|实际内容在变化，不能只统计重复抓取/重复包数量|
|捕获/读回耗时|某个局部阶段的时间，不能直接倒数成完整透视窗口帧率|
|完整成功|同时检查真实源、Alpha、动态更新、完整 UI、几何与时序、业务及恢复|

SurfaceView 相机通常独立提交，窗口 UI 为它保留孔洞；TextureView 相机通常由应用绘制器采样后混进同一个窗口；Flutter／GL 等也可能把 UI 与相机画进同一表面。**合成步骤存在，不保证此前已经生成独立、完整、可被外部订阅的 UI RGBA 流。** 结构依据见 [AOSP TextureView 架构](https://source.android.com/docs/core/graphics/arch-tv)；具体页面仍以实测为准。

研究约束逐步收紧到免 root、无需修改目标 APK、优先不安装助手 APK。早期曾安装独立实验助手，后来的纯 shell 路径才取消这一依赖。修改产品自身代码与修改目标应用 APK 是两件事；临时调整目标 View 后恢复，也不能称为完全只读。

## 四、色键、多背景与本地合成路线

### 4.1 rc17：先把本地透视做得可用

早期继承的架构将真实桌面与已知底色交错送入虚拟相机，在电脑端从应用回传画面里分离 UI，再用本地桌面合成。它使桌面交互不必完全等待手机回传，但透明度和前景颜色需要从混合 RGB 估计。

|编号|尝试及目的|结果与保留的结论|
|---|---|---|
|A01|提高小红书回传码率，观察格子/闪烁是否来自压缩|60M 下格子仍在，用户认为闪烁减少；相机输入编码仍是 8M，不能排除整个压缩链|
|A02|连续蓝底输入，排除桌面与底色交错影响|企业微信格子减少，仍有稀疏条纹；此条件没有桌面识别输入，不是扫码业务验收|
|A03|空间透射率模型与 32×64 稳定底板|受控 Camera2 场景明显更干净；不能直接推广到任意应用|
|A04|检查同色前景：蓝色不透明控件位于蓝底|单色路径会把真实蓝色前景一起删除，证实单底色歧义|
|A05|黑/白拟合，独立灰底验证|关闭受控应用扫描动画后，RGB MAE 0.3363/255，P95 1.5059/255；已知 40% 黑幕估计 Alpha 中位 0.40392|
|A06|真实企业微信三轮黑/白/灰取中位数|灰底预测 MAE 从 4.0865 降到 3.7415/255，仍有动态误差，不能视为静态模型适用于动画|
|A07|全分辨率静态预乘参考与软切换|首版有白边和横带；修订后用户认为明显改善且已够用，停止该轮画质精修；确认对象为受控原型|
|A08|核对视频矩阵与范围|加入 BT.601/709/2020、full/limited 一致处理；现场流为 matrix 5/limited，没有证明矩阵错误是主要根因|

校准遮罩为独立本地覆盖层：五层定位环和像素字只覆盖实际相机区域，等首张有效本地合成后约 180ms 淡出，避免露出传输中的校准图。它改善体验与首帧门控，不提高 Alpha 解的真实性。rc17 的 8M/32M 输入码率对照、等亮度暗红/蓝底验证曾准备，但没有完成，不列作实验结果。

原始依据：[rc17 抠像实验](rc17-perspective-matting-experiments.md)、[校准遮罩](rc17-calibration-mask.md)。

### 4.2 rc18：自动校准与动态颜色问题

自动流程为几何定位后，等待真实返回的蓝、黑、白、灰画面，各取 8 个有效样本，排除明显变化的像素，工作线程求解参考层，GPU 将稳定参考与实时特效融合。采样有 6.5 秒超时和像素上限，尺寸、色彩元数据或新相机调用会重建参考。

|编号|尝试及目的|结果与保留的结论|
|---|---|---|
|A09|自动多底色取代手工参考图|成为 rc18 入口能力；轻微白边、条带及亮度自适应 UI 仍可能存在|
|A10|修复企业微信正式入口扫码失败|同进程仅改自然竖屏起始即恢复识别；修订正式入口 10fps 两次成功，1fps 诊断四次成功|
|A11|红/蓝时序成对观测，加运动匹配|实机出现严重闪烁、格子和条纹，画质门槛失败，未继续扫码验收；撤回并恢复蓝底基线|
|A12|调查广播级键控、保护遮罩、Key/Fill 与独立 Alpha 传输|借鉴前景保护和透明度/颜色分别处理；没有找到可直接替换、免 root 通吃第三方动态 UI 的组件|

A10 的直接依据是启动方向对照；根据几何映射推断，预览看起来正常时，送给识别器的相机缓冲仍可能形变。没有保存当轮编码前缓冲，形变倍数仅为推断。不能把它写成所有扫码失败均由方向造成。

A11 约有 3034 个配对处理样本，最后计数曾到 3098 次配对；相关性高也没有保证视觉正确。局部 CPU/GPU 耗时仅为处理成本，既不是端到端延迟，也不是新旧算法受控性能结论。

蓝色扫描线与蓝底冲突促使后续转向原生 UI；单纯延长初始校准或换用更强阈值，不能消除单帧同色歧义。

依据：[自动校准](rc18-automatic-camera-calibration.md)、[扫码方向对照](rc18-wework-scan-verification.md)、[行业颜色保留调研](rc18-color-preservation-research.md)。A11 的原始资料为历史研究目录 `rc18-temporal-20261027/EXPERIMENT_RESULTS.json` 及 Alpha/底色统计，现已保存为脱敏历史报告，入口见[历史资料索引](perspective-camera/README.md)。

## 五、原生 PNG 与实时动态区双通道

### 5.1 原生 UI 可读，但逐帧 PNG 很慢

在 K80 企业微信，通过 shell 的 IWindow DUMP/CAPTURE 让应用重绘 View，取得了按钮、黑幕和蓝色光带的真实 Alpha。相机 SurfaceView 的独立画面不在这份 UI 重绘中。

|编号|尝试及目的|结果与边界|
|---|---|---|
|B01|1440×3206 整页原生 PNG|196 帧的抓取中位约 613ms，约 1.6fps；证明真 Alpha，不满足高速|
|B02|只抓动画 View／两个 CAPTURE 并行|动画 View 仍覆盖整页；双请求每两帧约 1.01～1.07 秒，没有明显提速|
|B03|64 像素脏块 PNG 打包|19 个差分帧总量只减少约 6%，电脑计算中位约 170ms；未接入运行路径|
|B04|降低物理像素但保留逻辑 dp|576×1280/240 下 90 秒收到 765 帧，约 8.49fps，抓取中位 116ms；固定尺寸场景用户接受|
|B05|窗口像素匹配与 flex/DPI 联动|以输出/窗口实际需求确定 PNG 尺寸，并重绑新 DecorView；用户确认放大缩小后恢复|
|B06|额外缩到 432×960|抓取约 70～90ms，但文字明显模糊，未选用|
|B07|CAPTURE_LAYERS 获取小组件边界|可提供按钮/文字保护区，但一次约 700～835ms；不是高频全页取流|

PNG 生成之后再差分，无法消除目标进程已经支付的整页重绘与编码成本。按 UID 捕获也不能分开同 UID 的相机和 UI。小米 miCaptureLayers 虽较快，当时得到全不透明合成图，不能作为原生 UI 来源。

### 5.2 inverse1～6：逐轮保留了什么、撤回了什么

混合方案用低频原生 PNG 保住静态界面，再从较快视频中补动态特效。初期企业微信原生 PNG 固定约 2fps，真实桌面输入 1fps，相机请求约 28～29fps。这些速率描述不同环节。

|编号|候选|实测反馈与变化|
|---|---|---|
|B08|组件小矩形用 PNG，其余实时色键|色键残影弥散出矩形，背景有色差；质量失败|
|B09|inverse1：默认全页 PNG，运动区用视频|运动掩码永久累积，出现随扫描形状扩张的色差痕迹|
|B10|inverse2：预热后固定支持范围、约束背景|用户确认痕迹消失，动态颗粒、块状或锯齿仍明显|
|B11|inverse3：实时增量做 5×5 平滑|仍有明显颗粒/块状，该项处理撤回|
|B12|inverse4：保留原色键路径扫描线 RGBA|避免混合阶段改变主体对比度；尾部仍脏|
|B13|inverse5：低能量蓝色尾部做邻域置信度渐隐|用户接受尾部改善，但它依赖颜色；量化表明弱柔光被大幅删去|
|B14|inverse6：学习视频自己的背景，只将动态正增量加回原生基底|取消蓝色通道特调，离线与 GPU 测试通过；实机继续迭代，最终得到可接受结果|
|B15|自动感知二维码／纸质名片模式切换|结构指纹变化后更新组件边界、暂停混合并重学；同数量组件也可能有不同矩形，不能只比较数量|
|B16|修正 inverse6 清洁掩码初始化顺序|首帧模型曾清空预填掩码，覆盖率仅 36.1%；将填充移后升至 93.2%，用户确认扫描截断及上方残影消失|

inverse6 的核心形式为 `out = native + active × max(video - model, 0)`，在预乘空间处理，运动范围和置信度控制参与区域。它只恢复“加亮／加 Alpha”的正增量；变暗、移除内容仍受低频原生 PNG 更新限制。它不是完整原生动态 RGBA 流，也没有消除视频压缩误差。

离线 15 位置合成仿真中，inverse5 的光晕 Alpha 增益约 0.246，inverse6 设计参数约 1.000；这是受控仿真，不是真机实时测量。提高阈值可以减少噪点，也会损失最外缘柔光，不能只优化背景误差指标。

|编号|尝试|结果与边界|
|---|---|---|
|B17|rc20 客户端自动拉起设备探针，PNG+区域元数据双通道默认化|不再手动运行 collect；低分辨率场景从人工流程约 20.5 秒缩到约 5.0 秒可用，用户接受|

rc22 中微信 PNG 全 A255 时不启用双通道，是对无有效 Alpha 来源的拒绝，不是原生透明成功。GUI 缩小窗口时的锯齿反馈当时仍属待调查，不作已证实根因。

## 六、真正的原生 Alpha：窗口、渲染器与能力规则

### 6.1 独立图层与窗口状态对照

|编号|尝试|实际结果|
|---|---|---|
|C01|VirtualDisplay → ImageReader 能否保留 Alpha|透明测试 Activity 可保留 0/64/128/255；真实企业微信 378 帧整屏输出全 A255，同窗 View CAPTURE 有半透明 UI|
|C02|自有 SurfaceControl 分层，排除相机／直接捕获 UI|576×1280 四档 Alpha 各 184320 像素，精确匹配；同 UID 过滤无法分开两层|
|C03|WindowOrganizer 同步事务取得真实窗口句柄|真实微信窗口可捕获；必须匹配 Binder 和真实 layerId。得到窗口根不等于得到相机子层或生产者 buffer|
|C04|清 SurfaceControl OPAQUE 位、隐藏 TextureView、清背景、改窗口 format、切 freeform|早期平板微信对照均未得到原始 UI Alpha；整层 alpha=0.5 可得半透明，但只证明捕获通道能承载 Alpha|
|C05|独立 HardwareRenderer 复现旧帧残留|先画黑底，再移除背景但 opaque=true，仍全 A255；同 renderer 改 opaque=false 后恢复准确透明底与半透明矩形|
|C06|用 Activity 场景过渡触达目标进程透明转换|独立助手 true→false→true 的 renderer 对照通过；真实平板微信取得 8 张变化的原生 RGBA，早期重复出现应用主动退出|
|C07|排除“只在初始化前几帧有效”|先等待扫码 15 秒，再过渡；过渡后 31.7 秒仍有 Alpha，约 33 秒局部文字隐藏/恢复可被像素读回观察|
|C08|无线传输及离屏合成吞吐|576×1280 Alpha XOR 差分约 66.85 包/秒、57.30 次有效变化/秒，532/532 CRC；完整 RGBA+软件合成约 29.94/s|
|C09|用 NumPy 更直接的预乘公式代替 Pillow|像素近似正确，但软件合成更慢，整链路约 22.7/s；保留较快基线|
|C10|取消独立助手 APK，使用设备已有系统组件完成场景协议|后续纯 shell 路径在 K80 微信接通，进入 rc23 能力机制；不代表所有应用接受场景转换|

C05 说明 opaque=true 可省略透明清屏，**不等于每次把 A 强行写成 255**。新空缓冲也曾出现透明及后续累积，因此必须关注缓冲历史。

C06 最初使用独立实验 APK，并未改微信 APK。EXIT_SELF/System.exit 只证明应用主动退出；没有证据定为反外挂，也不能归因于唯一过渡步骤。C07 排除初始化快照解释，没有解决所有重复稳定性问题。

C08 中最快的捕获 API 曾重复返回约 255～393 次/秒，实际源变化约 60/s；完整流包含重复包和末尾积压，不能宣称真实 Windows 窗口达到同样帧率。该阶段还没接入真实产品窗口和 RGB 视频同步。

依据：历史 `srgb-alpha-research-20261028` 中的《调研结论_sRGB与免root实时Alpha》《微信原始Alpha实验记录》《内部渲染器研究记录》《场景过渡原生Alpha实测记录》《初始化假说_延时与主动重绘验证》《原生Alpha吞吐上限实测_20261030》。当前仓库中的后续归纳见 [rc23 能力报告](RC23_CAPABILITY_REPORT.md)。

### 6.2 rc23：从单例配方到结构能力机制

rc23 使用现场 UID、window token、display、预览结构、可恢复范围和真实 Alpha 判定，不以机型、ROM、版本或包名白名单决定支持。历史配方只提供候选步骤，不能复用旧对象、旧坐标或旧图层编号。至少两帧有效 Alpha 后才启用叠加，来源或窗口代次变化时撤销旧基准。

|编号|修订|结果与限制|
|---|---|---|
|C11|GPU SRC 读回代替软件 Bitmap/getPixels 往返|K80 微信 1440×3200 从约 6～8fps 提到常见 22～28fps；8 分钟约 11099 有效帧无补丁错误，中位 22.9fps，仍会下降|
|C12|整页关键帧+无损变化行补丁、epoch、CRC 与预乘叠加|跨 Java/C 的 80 帧及 D3D11 像素测试通过；降低数据处理成本，不改变目标来源是否可分离|
|C13|Engine 9 独立 ruleKey、P3→sRGB GPU 读取|小红书 3200×2136 特定场景接通，中位源速率约 16fps；A8 精确，RGB 转换最大量化差 1|
|C14|Engine 10／11 抖音动画累积及长图层名匹配|独立原始捕获已见累积；按 layer ID 连接完整名称和 UID 摘要后，system-scene 窗口源成功，用户确认重进与超过五分钟正常|
|C15|Engine 12 只读检查五个失败应用，候选叶节点及启动方向|识别 React 容器与真相机叶节点、根页恢复困难和共享表面；没有一次性修复五应用|
|C16|Engine 13 根背景资源恢复、原始 Surface order、变换相机范围、共享整页 UI 拒绝|实现候选；themeResource 不是原 Drawable 对象完全恢复，后续真实失败仍保留|
|C17|Engine 14 转场能力预检、层级后备、APK 资源路径反查|支付宝不再被机制结束，但仍蓝底；未声明所有兼容问题解决|
|C18|Engine 15 用 Perfetto 含虚拟显示快照取得真实层级，新增 window-direct|纠正默认 SurfaceFlinger proto 不含 Steam 虚拟屏的问题；Steam 句柄取得后仍没有 Alpha|
|C19|Engine 16 失败后 suspended，限制同窗口反复场景转换|Steam 三阶段仍全 A255，但场景转换不再循环；失败有完整 Alpha 统计，生命周期修复与兼容失败分别记录|

Steam 的 ReactSurfaceView 是容器，真正相机 SurfaceView 更深；V次元的一个 SurfaceView 却承载 Flutter 整页内容。仅按名字包含 SurfaceView 选相机，既可能选错容器，也可能把整个 UI 隐藏。

成功档案不能替代后续现场验真：相同 Activity 在物理相机、虚拟相机、布局或版本变化后可能改用另一种预览。

依据：[原生通道](RC23_NATIVE_ALPHA.md)、[能力报告](RC23_CAPABILITY_REPORT.md)、[档案与匹配](RC23_AUTO_ALPHA_PROFILES.md)、[Engine 9～16 记录](RC23_RULES_DESIGN.md)、[失败应用只读探测](handoffs/结果_失败应用结构探测_20261030.md)、[Engine 13/14 调查](handoffs/调查_Engine13失败与Engine14修正_20261031.md)。

## 七、rc24：尽量保留原始绘制，在读出阶段分离

|编号|尝试|结果与边界|
|---|---|---|
|D01|Steam 原始整树 UI 重绘，验证 Alpha 是否本来存在|预览存在时透明/半透明丰富；预览暂停后整树全不透明。不能由系统捕获 A255 推断 UI 没有 Alpha|
|D02|自有 SurfaceView 验证天然孔洞与 alpha/Z 的关系|下层 alpha=1 正常打孔；alpha=0 或置顶会失去孔洞，解释旧路径为何需要越来越多背景清理|
|D03|从同步事务 Parcel 直接导入 GraphicBuffer|自有 64×64 四档 Alpha 精确；真实 Steam 同步回调只有层状态，没有 buffer 变更位或像素 FD|
|D04|标准 setExcludeLayers 排除相机子树|自有层逐像素正确；真实 Steam 仅得到窗口根，未取得 Bounds/相机子层 Binder，真实路径未接通|
|D05|ViewDebug CAPTURE 做全树重绘|Steam 五次命令中位 289ms；真实 A8，但约 3fps 量级，只作为诊断|
|D06|CAPTURE_LAYERS 后逐层重组|31 个视图约 2.42 秒；单层快照缺少整树打孔语义，不能简单拼回原始带孔 UI|
|D07|ScrollCapture → 调用方 Surface，绕过 PNG|Steam/微信固定扫码页无 target；平板 Bilibili HD 滚动页面连续 8/8 原始 RGBA 帧，RTT 中位约 84ms，但范围受 scrollBounds 限制|
|D08|Engine 17 每窗口一次有界重绘诊断|区分“UI 重绘有 Alpha，捕获路径不透明”和“重绘不透明”；不把 PNG 接进实时流，也不标为兼容成功|

D03 不能称“取得原始生产者缓冲”：窗口组织器事务与应用 BLAST 提交像素不是同一条路径。D04 需要真实 Binder 句柄，layer ID、IWindow token 和输入 token 不能互换。

D07 当时的串行循环含等待，实际约 1.4～1.8fps；7～11fps 是依据 RTT 的流水化估算，未实测达成。样本页本身全不透明、顶部不在捕获区，没有验证完整透明扫码 UI。INCLUDE 提示不会自动给任意固定 View 安装采集回调。

**历史结论修正：** rc24 报告曾将句柄受限概括成“不 root 下该方向不可行”，这个表述太宽。它只约束当时检查的标准句柄路径；rc25 的厂商名称过滤随后绕开了对子层句柄的需求。

依据：[合成前 UI 研究](handoffs/调研_合成前UI原生Alpha_20261031.md)。第二轮详细原始报告 `RC24_UI_REDRAW_RESEARCH.md`、`RC24_NATIVE_ALPHA.md` 已归档为脱敏副本，见[RC24 重绘研究](perspective-camera/history/rc24/RC24_UI_REDRAW_RESEARCH.md)及[版本说明](perspective-camera/history/rc24/RC24_NATIVE_ALPHA.md)。

### 8.2 名称过滤：保留天然孔洞，不改目标页面

|编号|尝试|结果与边界|
|---|---|---|
|E06|枚举厂商 setExcludeOrIncludeLayerNames 与 setCaptureMode|两台小米特定构建实际存在；离屏语义对照证实 mode1 排除、mode2 包含，子串匹配|
|E07|按现场图层父链排除完整相机子树|只排容器会留下 BLAST/背景；排完整树无需相机子层句柄，不改目标 View/Z/背景/Activity|
|E08|真实企业微信与 Steam 无损流|K80 企业微信 600 帧约 24.72fps，Steam 静态 UI 240 帧约 31.34fps，全部主机 CRC；企业微信另 1800 帧约 14.70fps|
|E09|跨设备/应用结构矩阵|两台小米企业微信通过；普通相机页的小红书、支付宝、向日葵为 TextureView，V次元共享 Flutter 表面，名称过滤不适用|
|E10|小红书历史成功复核|同版本平板小红书在产品虚拟相机会话可见 SurfaceView，旧 surface-zalpha 再次连续取流；不能把普通相机的过滤负例外推为产品全不支持|

名称过滤是新捕获源原型，未成为正式 GUI 全自动覆盖承诺。其主机吞吐包含捕获、读回、编码、ADB、重建与校验，不含 GUI 渲染。Steam 当时 UI 静止，不能据 31.34fps 说每秒有同数量独立动态内容。

两台现代成功设备都是小米系 Android16／OS3.0.309.0。AOSP 有标准句柄排除，没有本次字符串名称参数；近期三星框架样本支持句柄排除，Oplus 有其他截图接口线索，均没有同等名称过滤的现代实机成功证据。老华为 Android8 缺少接口，只说明该旧设备，不代表现代华为或其他品牌。

研究矩阵是定向选样，不能折算市场覆盖率，也不能宣布接口为小米原创或独占。

依据：[名称过滤实验](../research/general-rgba-20261101/README.md)、[泛用性报告](图层过滤泛用性调研报告_20261101.md)、[近期 ROM 与上下文复核](RC25_性能与近期ROM调研_20261101.md)。

## 九、支付宝与更底层获取方案的后续攻关

### 9.1 先确认是真实投屏，再讨论 Alpha

|编号|尝试|结果与边界|
|---|---|---|
|F01|正式虚拟相机会话复核|支付宝确实占用本轮虚拟相机，仍为 APTextureView，无独立相机层；所试镜像/窗口源全 A255|

F05/F06 的约 20ms 是捕获+读回中位成本，不含完整统计、传输和最终显示。研究客户端部分会话只显示普通 H264 监视画面，没有将外部探针 RGBA 送回 PC，屏幕观感不能充当无损 Alpha 流显示验收。

|F11|临时不透明洋红背景负对照|残留明显收敛，支持透明化后的完整覆盖/清除状态有关；洋红背景不是透明方案，也没有唯一证明 HWUI 根因|
|F12|INVALIDATE、根 Alpha0.999、黑资源→透明资源并重排|有效相机 25～28fps 场景中，各 24 帧像素判据通过为 5/0/0；基线 12 帧有 2 阳性，恢复后另 60 帧全阴性。三者都未形成修复|
|F13|补充动态准入与探针 rebind 修正|把相机错误页/静止源排除；修正辅助检查引用已释放 SurfaceControl 的问题，编译通过，但修正分支未再次上机验收|

F12 是固定顺序小样本，不能据 5/24 宣称 INVALIDATE 有因果收益；根 Alpha0.999 有 7 张非全不透明但判据全未过，说明“有 A<255”不足以表示有正确透明 UI。

### 9.3 相机启动失败的一个独立根因

|编号|尝试|结果与边界|
|---|---|---|
|F14|同支付宝进程、同虚拟相机，20:9→16:9 显示配置对照|20:9 请求 Deferred PRIVATE1600×720 + YUV1920×1080，被 endConfigure 拒绝；16:9 重开改为1280×720 +1920×1080，持续约29fps|
|F15|独立 Camera2 普通／Deferred 输出复现|Deferred1600×720组合失败；Deferred1280×720组合成功；普通Surface请求1600×720却实际得到1280×720，解释初期对照为何没复现|
|F16|尝试 RGBA_8888 虚拟相机输出／透明输入方向|本机1920×1080 RGBA输出被拒，YUV单流3秒87张；AOSP RGBA→YUV转换不传输入Alpha，没有实际注入Alpha0，未穷尽PRIVATE内部格式|

这是相机输出配置问题，与 UI Alpha 获取、扫描残影分别成立。只有 A→B 对照，没有 A→B→A；应用为何选择未公布尺寸也没有唯一确认。16:9 不是已发布的全应用布局修复。

### 9.4 再试双背景反求，验证“更一般”是否真的成立

F17 在有效 16:9 支付宝相机中，不改目标 View，分别送黑、白、灰、暗红、重复黑，每阶段取 3 张原始窗口，共 15 张。黑白拟合，灰/红/重复黑独立验证。

全图误差≤8的比例约96%，但可见非黑 UI 证据子集通过率仅约23.65%／34.26%／31.59%；重复黑场有119024像素变化超过8。大片背景抬高了全图指标。线性 sRGB 对照没有消除动态误差；相机颜色响应未完整标定，也没有原生 Alpha 真值。

结论是静态元素可重建、动态通用流未通过。该思想在 rc17 已存在，本轮新增的是真实虚拟相机及独立验证数据，不能写成新发明。它属于估算，不是原生 Alpha 导出。

依据：[初轮组件实验](../research/alipay-texture-20261102/REPORT.md)、[真实 PC 投屏](../research/alipay-texture-20261102/REAL-CAST-FOLLOWUP.md)、[时序与残留](../research/alipay-texture-20261102/TEMPORAL-AND-TRAILS.md)、[透明清除接口复核](../research/alipay-texture-20261102/COMMUNITY-OPACITY-FOLLOWUP.md)、[有效动态三候选](../research/alipay-texture-20261102/DEADLINE-VALIDATION-20261103.md)、[相机配置与双背景](../research/alipay-texture-20261102/FOUNDATION-ACCESS-20261103.md)。

## 十二、后来必须纠正或限定的判断

1. **“免root拿不到原生Alpha”过强。** 多个真实应用样本已经取得；难的是稳定、通用地触达正确来源。
2. **“有RGBA格式就有UI透明度”错误。** 全A255、整层统一半透明、空白全A0都不能证明正确UI分离。
3. **“SurfaceView存在就能排相机”错误。** 它可能是不可见候选、带子节点的容器，或承载整个Flutter界面。
4. **“窗口opaque标志、format和renderer opaque相同”错误。** 不同层的状态需要分别验证，改元数据不保证目标绘制器透明清屏。
5. **“隐藏相机就是读取原始UI”不准确。** 可能破坏天然打孔，引出清背景和恢复问题；名称过滤才在已测结构中保留原绘制状态。
6. **“句柄路径不通，所以厂商没有其他入口”过强。** rc25名称过滤是反例；同样也不能从两台小米推广到所有Android。
7. **“高速API调用等于高速新帧/最终显示”错误。** 重复捕获、重复包、设备循环、主机重建与真实呈现必须分开。
8. **“全图96%重建正确就够了”不成立。** 大背景会掩盖UI区域的大误差；必须单独检验实际前景和独立背景条件。
9. **“CPU/GPU一致或CRC通过就代表方案正确”不充分。** 错源、不完整UI、静止错误页也能完全一致。
10. **“应用退出必然是崩溃/反外挂”没有依据。** 曾有机制主动结束Activity、EXIT_SELF、错误窗口选择等不同原因。
11. **“温控状态0能排除温控”不成立。** 厂商策略、负载和调度未被统一观测；8.7%代码收益与热状态漂移分开。
12. **“SKP机制本身必须root”过强。** 属性文件采集有debug门槛，自有进程回调可在debugging=false下导出；目标进程入口仍缺失。
13. **“一定已有一张完整UI纹理，只差拦截”没有证据。** UI可能以RenderNode/绘制命令存在，直到和相机一起画入窗口。
