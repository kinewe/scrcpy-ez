# RC.18 企业微信扫码：初始显示方向对照

2026-10-27，基于 RC.18 的 `20261027-flex1` 修订继续测试，设备为 REDMI K80 / Android 16。

## 已确认的实机结果

| 启动方式 | 输入 | 结果 |
| --- | --- | --- |
| 自然竖屏、新进程、不启用 flex | 10fps 交错桌面与蓝底 | 用户确认识别成功 |
| 自然竖屏、新进程、启用 flex | 1fps 交错桌面与蓝底 | 用户确认连续四次识别成功 |
| 正式入口：横屏起始、复用进程、启用 flex | 10fps | 透视可见，无法识别，之后用户观察到画面卡住、可以截图 |
| 同正式入口参数、完整日志诊断、复用进程 | 10fps | 持续更新，但无法识别 |
| 上述同一会话，切成连续桌面输入 | 30fps，无蓝底交错 | 桌面方向看起来正常，仍无法识别 |
| 仅改自然竖屏起始、继续复用同一进程、启用 flex | 10fps | 用户确认恢复识别 |
| 修订后 RC.18 正式启动器，实际命令为 `--new-display=1440x3200/600 --flex-display` | 10fps | 用户确认两次均扫码成功 |

测试二维码为相同的 HTTPS 测试地址，灰底窗口显示，二维码完整落在扫描区域。未改变企业微信数据，没有重新登录。最初沿用旧进程曾实际打开物理相机 0，后续系统虚拟相机两次初始化卡在 `camera-create`；用户重启并重新连接后恢复，属于另外的生命周期问题。

## 定位依据

GUI 的 `nativeRes()` 为传输档案把分辨率规格归一成宽≥高。原应用窗口默认据此从 `3200x1440/600` 起始，再因扫码 Activity 的方向要求切换成竖向。失败会话校准为约 `[-0.997,0,0,-1,0.999,0.999]`，成功自然竖屏会话为约 `[0,-1,1,0,1,0]`。

相机输入固定为 1920×1080，预览约为 582×1296。依据失败映射的局部缩放比例计算，屏幕上正方形二维码可能在原始相机缓冲中被横向拉宽约 4 倍，预览变换又将它压回正方形。该形变比例是根据映射计算的推断，本轮没有直接保存编码前原始相机缓冲；不能将电脑预览正常视为手机识别源无形变。

同一进程、10fps、flex 均保留，仅改初始方向即恢复识别，是本次启动方向修复的直接对照依据。不能把之前的失败归结为微信相机只请求30fps，也不采用提高码率或缩短校准来处理。

## 修订范围

仅在企业微信透视相机窗口没有指定比例时，依据设备自然方向生成初始尺寸。保留长边档位、DPI、flex、音频、码率、FPS、送帧档位和进程复用；显式长宽比仍优先，其他应用与主投屏不受此兼容分支影响。自然横向设备也不强制竖屏。

实际参数回归包含手机自然方向、冷缓存、手动 DPI、自定义横屏比例、自然横向平板、关闭透视和其他应用隔离。目标 Go 回归通过，启动器已重新构建。

用户确认现有校准时长适中、动画有仪式感，因此不缩短多底色采样，不修改遮罩、淡出或送帧默认值。

## 待完成和已知限制

修订后的正式入口已由用户复测，两次均扫码成功；设备端命令也已确认启用自然竖屏、自动 DPI 和 UI 保留路径。本次正式复测使用了显式重启应用的入口，诊断对照另有继续复用原进程成功的记录，不将两者混为同一试验。

之前正式会话卡住时的完整错误日志未保留，不能宣称仅调整初始方向已经解决所有相机流中断。用户另指出企业微信蓝色扫描线在本地透视里变色，蓝底分离与同色动态前景可能冲突，尚未修复，不能把该现象当作二维码不能识别的已证实原因。
